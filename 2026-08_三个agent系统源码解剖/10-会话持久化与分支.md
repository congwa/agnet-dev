## 0. 先搞清楚：这是个什么东西

想象你在用一个只能靠嘴说的工程师干活。你说一句，他做一堆事，你再说一句。整个过程里，「你们俩共同知道什么」全部存在这一串对话里——模型本身是无状态的，每一轮都要把完整历史重新塞回去。

于是「会话」就是这串历史。而会话持久化，就是把它写到磁盘上。听起来平平无奇，但它撑起了四件完全不同的事：

1. **崩溃恢复**。终端被误关、SSH 断线、机器重启。没存盘，两小时的探索归零——不只是聊天记录没了，是 agent 读过哪些文件、试错过哪些方案、结论是什么，全部要重新烧一遍 token。
2. **换设备 / 换进程接着干**。早上在笔记本上开了个头，下午想在服务器上接着跑。
3. **事后审计**。这个 agent 到底执行了哪条 `rm`？它是在哪一步决定改这个文件的？出了事故要能翻账。
4. **回到某一步重来**。这条最重要，也最容易被低估。

第 4 条值得展开。agent 干活的失败模式不是「答错了一道题」，而是「在第 6 步走岔了，后面 20 步全在错误的地基上盖楼」。人类的自然反应是：**回到第 6 步，换个说法，重来一次**。如果 harness 只能「继续」不能「回退」，用户唯一的选择就是开一个新会话，把前 5 步重新说一遍——前面的上下文全丢了。所以能不能廉价地回到任意历史点，直接决定了 agent 是「一次性的」还是「可迭代的」。

实现这件事有两条基本思路，值得先分清：

**append-only 日志（事件溯源）**：只往文件末尾追加，永不修改、永不删除。每条记录是「发生了什么」。恢复 = 从头重放。优点是写入极简（一次 `append`，天然抗崩溃——最坏情况是最后一行残缺），审计天然完备，历史不可篡改。缺点是读取要扫全文，体积随时间单调增长，而且「当前状态是什么」不是直接可读的，得算出来。

**状态快照（checkpoint）**：每隔一个执行单元，把「当前完整状态」整个存一份。恢复 = 直接加载最近一份快照。优点是恢复 O(1)，任意一份快照都能独立复活。缺点是每份快照都存了大量与上一份重复的内容，且快照粒度决定了你能回退到多细的地方。

两条路都能做「回到某一步」：日志派是「把读取指针移到中间某条记录，然后从那儿开始追加新分支」；快照派是「加载第 k 份快照，从它派生一份新的」。本章三个项目正好把这两条路都走了，而且走出了三种很不一样的形态。

## 1. 为什么这件事很难

### 1.1 存什么粒度：消息、turn，还是状态变更？

最朴素的做法是存消息列表。但 agent 会话里发生的事远不止消息：用户中途换了模型、调高了 thinking level、触发了一次压缩、给某个节点打了个书签、某个扩展写了一份自己的状态。这些都不是「消息」，但恢复时全都要还原——否则你 resume 出来的会话，模型是错的、推理档位是错的、压缩点丢了。

反过来，粒度太细也有代价。如果把每次流式 delta 都记下来，文件会爆炸；如果把每个 UI 事件都记下来，解析器要处理一堆和语义无关的噪声。**必须有一份显式的「什么该持久化」清单**，而且这份清单本身会成为兼容性负担——今天决定不存的东西，明天想存就得处理老文件。

### 1.2 恢复不等于「把文件读回来」

恢复要重建的不是文件内容，而是**发给 LLM 的那份上下文**。这两者往往不同：

- 被压缩掉的历史还躺在文件里，但不能进上下文；
- 分支切换后，被放弃的那条支线躺在同一个文件里，也不能进上下文；
- 某些条目（扩展的私有状态）永远不进上下文，但要在重载时还给扩展。

所以文件是「全集」，上下文是「全集上的一个投影」。投影规则写错了，恢复出来的会话看起来正常，实际上模型看到的历史是错的——这类 bug 极难发现。

### 1.3 并发写

同一个会话文件可能被多个写者盯着：用户开了两个终端 resume 同一个 session；后台有个压缩/归档任务在重写文件；多 agent 场景下子 agent 从父会话派生。天真的「读全文 → 改 → 写回」在这些场景下会静默丢数据。append-only 缓解了一部分（并发 append 至少不会互相截断），但「谁是当前 leaf」这种可变指针仍然需要协调。

### 1.4 体积膨胀

coding agent 一次 `read` 可能返回 3000 行、一次 `bash` 可能吐几十万字符。这些原文都要落盘。一个跑了几小时的会话，JSONL 上百 MB 很常见；用了几个月的用户，`~/.xxx/sessions/` 几个 GB 也很常见。于是必须回答：冷数据要不要压缩？要不要归档？删除是硬删还是进回收站？以及最烦的——**列出「最近 20 个会话」时，能不能不读完所有文件？**

### 1.5 分支语义：fork 之后两条线怎么维护

假设你从第 6 步分了个叉。现在有两个问题：

- **物理上放哪儿**？两条支线放在同一个文件（一棵树），还是各自一个文件（两份拷贝）？同一文件省空间、便于对比，但文件内部就不再是线性结构了，所有读者都得懂树。各自一个文件简单，但会把公共前缀复制 N 份。
- **语义上，被放弃的那条支线算什么**？如果它只是「没被选中的路」，那忘掉就行；但如果你在那条路上试出了「方案 A 行不通，因为 X」，这个结论是有价值的，直接丢掉等于让 agent 重蹈覆辙。

## 2. Pi 的做法

### 2.1 一句话概括

一个 session 一个 JSONL 文件，**文件内部是一棵树**：每条 entry 带 `id` + `parentId`，「当前位置」是一个叫 active leaf 的指针；分叉就是把 leaf 指回祖先然后继续 append。在此之上提供三种语义不同的分叉命令（`/tree` / `/fork` / `/clone`），并把「选中一条历史 user 消息 → 文本回到编辑器 → 改完重发 = 开新分支」做成 TUI 一等公民。

### 2.2 机制拆解

`type` 一共九种（`session-manager.ts:144` 的 `SessionEntry` 联合类型）：

| type | 作用 | 是否进 LLM 上下文 |
|---|---|---|
| `message` | 用户/助手/工具结果/bash 执行 | 是 |
| `model_change` | 中途换模型 | 否，但决定恢复时用哪个模型 |
| `thinking_level_change` | 中途改推理档位 | 否，同上 |
| `compaction` | 一次压缩，带 `summary` / `firstKeptEntryId` / `tokensBefore` | 是（作为摘要消息） |
| `branch_summary` | 切分支时对被放弃支线的摘要，带 `fromId` | 是 |
| `custom` | 扩展的私有状态 | **否** |
| `custom_message` | 扩展注入的消息 | 是 |
| `label` | 给某个 entry 打的书签（`targetId` + `label`） | 否 |
| `session_info` | 会话显示名（`/name`） | 否 |

这张表本身就是对 1.1 的直接回答：Pi 选择「消息 + 显式的状态变更事件」这个粒度，而不是「只存消息」。`label` 和 `session_info` 也被塞进同一棵树里（而不是单独的元数据文件），这带来一个副作用——后面 `createBranchedSession` 得专门把它们摘出来重新挂链（见 2.3）。

在第一条 assistant 消息到达之前，什么都不写盘；一旦到达，用 `wx`（排他创建）一次性把内存里攒的全部条目倒出去，之后每条 append 一次。这解决的是一个很实际的体验问题：用户 `pi` 开一下、看两眼、Ctrl+C 退出，不应该在 `sessions/` 里留一堆空文件污染 `/resume` 列表。代价是**首个 turn 完成前崩溃 = 全丢**——对 CLI 场景可接受，对长时间批处理就未必了。

**恢复：从文件到上下文的投影**。`buildSessionContext()` 做两件事。第一，沿 leaf 一路走到根，拿到「当前分支路径」；第二，在这条路径上处理压缩：

`packages/coding-agent/src/core/session-manager.ts:418`

```typescript
export function buildContextEntries(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionEntry[] {
	const path = buildSessionPath(entries, leafId, byId);
	let compaction: CompactionEntry | null = null;

	for (const entry of path) {
		if (entry.type === "compaction") {
			compaction = entry;
		}
	}

	if (!compaction) {
		return path;
	}

	const compactionIdx = path.findIndex((entry) => entry.id === compaction.id);
	if (compactionIdx < 0) {
		return path;
	}

	const contextEntries: SessionEntry[] = [compaction];
	let foundFirstKept = false;
	for (let i = 0; i < compactionIdx; i++) {
		const entry = path[i];
		if (entry.id === compaction.firstKeptEntryId) {
			foundFirstKept = true;
		}
		if (foundFirstKept) {
			contextEntries.push(entry);
		}
	}
	contextEntries.push(...path.slice(compactionIdx + 1));
	return contextEntries;
}
```

注意这里的顺序：摘要条目排**最前**，然后才是 `firstKeptEntryId` 之后保留的原始条目，最后是压缩之后新增的。也就是说被压缩掉的历史依然完整躺在文件里（审计可用），只是不进上下文。同一个文件既是审计日志又是上下文来源，靠这层投影分开——这正是 1.2 说的那件事。

模型和 thinking level 的恢复走另一条线：`getSessionContextSettings()`（`session-manager.ts:362`）在完整路径上做一次 fold，后写覆盖先写，且 assistant 消息自带的 `provider`/`model` 也参与——所以哪怕没有显式的 `model_change` 条目，恢复出来的模型也是对的。

**三种分叉**。这是 Pi 最有辨识度的部分，也是最容易混淆的部分：

| | `/tree` | `/fork` | `/clone` |
|---|---|---|---|
| 产物 | **同一个文件**，只移动 leaf 指针 | 新文件 | 新文件 |
| 选择界面 | 完整树（可折叠、可过滤、可搜索） | 只列 user 消息 | 无（就用当前 leaf） |
| 切点 | 任意 entry | 选中 user 消息的**父节点** | 当前 leaf（`position: "at"`） |
| 分支摘要 | 可选（三选一：不要 / 默认 prompt / 自定义 focus） | 无 | 无 |
| 典型用途 | 在原地探索多个方案，保留全部支线便于对比 | 从某句旧 prompt 重新起一条独立的会话 | 在继续之前先存一份当前状态的副本 |

```sql
-- after a new owner takes over the session.
CREATE TABLE IF NOT EXISTS writer_leases (
	session_id TEXT PRIMARY KEY,
	owner_id TEXT NOT NULL,
	fence INTEGER NOT NULL,
	expires_at_ms INTEGER NOT NULL
) WITHOUT ROWID;
```

配套的获取逻辑是一条带条件的 upsert：

`packages/session-backends/sqlite-node/src/sqlite/storage/writer-leases.ts:15`

```typescript

			VALUES (?, ?, 1, ?)
			ON CONFLICT(session_id) DO UPDATE SET
				owner_id = excluded.owner_id,
				fence = writer_leases.fence + 1,
				expires_at_ms = excluded.expires_at_ms
			WHERE writer_leases.expires_at_ms <= ?
```

租约过期才能被抢，抢到就把 fence 加一；续约和释放都要求 `owner_id + fence` 都匹配。这是教科书式的 fencing token——一个卡住的旧写者醒过来之后，它手里的 fence 已经过期，写不进去。这正好补上了 1.3：**JSONL 文件后端没有这个机制**（`session-manager.ts` 里搜不到任何 lock/flock），两个进程同时 append 同一个 session 文件是未定义行为。SQLite 后端存在的理由之一就是这个。

### 2.3 代价与适用边界

- **单文件树 = 单文件锁**。所有分支挤在一个 JSONL 里，多进程并发只能靠外部协调。默认后端不做这件事。
- **全量加载**。`SessionManager` 打开文件时把所有 entry 读进内存（`loadEntriesFromFile`，1MB 缓冲逐行解析），并建 `byId` 索引。对几百 MB 的会话，启动会明显卡；`getEntries()` 每次还做一次 `filter` 拷贝。
- **文件级版本迁移**。v1（线性）→ v2（树）→ v3（`hookMessage` 改名 `custom`），迁移在加载时就地做完并整文件重写（`_rewriteFile`）。好处是运行时代码只需处理一个版本，代价是打开老会话有一次全量重写。
- **cwd 编码进目录名**：项目挪个位置，历史就「消失」了（文件还在，只是 `/resume` 找不到）。
- **树本身没有 GC**。放弃的分支永远留在文件里。对「事后审计」是优点，对磁盘占用是缺点，且没有内建的清理入口。

## 3. Codex 的做法

### 3.1 一句话概括

一条会话 = 一个按日期分目录的 append-only JSONL「rollout」文件，**严格线性、不存树**；分支通过「复制一个前缀到新文件」或（分页模式下）「用 `(thread_id, ordinal, byte_offset)` 引用父文件的前缀」实现；文件之外另建一个 SQLite 状态库作为**可重建的索引**，用于列表、搜索、归档，JSONL 始终是唯一真相。

**反向 JSONL 扫描器**。这是本章最值得单独拿出来讲的工程技巧。问题是：一个 200MB 的 rollout 文件，我只想知道**最后一条**记录是什么（比如「最新的 ordinal 是多少」「这个 thread 最近改名成什么了」）。从头读到尾是 O(文件大小)，完全不可接受。

`codex-rs/rollout/src/reverse_jsonl_scanner.rs:19`

```rust
/// Read-only scanner for newline-delimited JSON records, starting from the end.
pub struct ReverseJsonlScanner<R> {
    reader: R,
    next_chunk_end: u64,
    chunk_position: usize,
    chunk: Vec<u8>,
    record_reversed: Vec<u8>,
    max_record_bytes: Option<usize>,
    discarding_oversized_record: bool,
}
```

原理：从文件末尾往前，一次 `seek` + 读 64KB 一块；在块内**从后往前**找 `\n`；找到就说明凑齐了一条完整记录（可能横跨多块，所以要把碎片按倒序累积到 `record_reversed` 里，最后整体 reverse 再交给 serde 解析）：

`codex-rs/rollout/src/reverse_jsonl_scanner.rs:94`

```rust
            let chunk = &self.chunk[..self.chunk_position];
            if let Some(newline_position) = chunk.iter().rposition(|byte| *byte == b'\n') {
                let fragment = &chunk[newline_position + 1..];
                if !self.discarding_oversized_record {
                    if self.max_record_bytes.is_some_and(|max_record_bytes| {
                        self.record_reversed.len().saturating_add(fragment.len()) > max_record_bytes
                    }) {
                        self.record_reversed.clear();
                        self.discarding_oversized_record = true;
                    } else {
                        self.record_reversed.extend(fragment.iter().rev().copied());
                    }
                }
                self.chunk_position = newline_position;
```

三个细节值得学：

1. **`with_max_record_bytes`**。rollout 里可能有一条 50MB 的工具输出。如果调用方只想找一条小小的元数据记录，没必要把它读进内存——超限就直接丢弃继续往前扫（`discarding_oversized_record`）。
2. **`ScanOutcome::Rejected`**。解析失败不中断扫描，返回 `Rejected(err)` 让调用方决定跳过还是报错。文件末尾半行残缺（上次崩溃留下的）是常态，不能因此让整个 resume 挂掉。
3. **`new_at(reader, end_byte_offset)`**。可以指定「逻辑末尾」在哪个字节，从而只扫一个**冻结的前缀**，忽略之后追加的内容。这一条直接服务于下面的引用式 fork。

使用者比如 `ordinal.rs`（找最新序号，用来续写）和 `session_index.rs`（找最新的会话名，因为改名也是 append-only、后写覆盖先写）。

### 3.3 代价与适用边界

- **不存树**。Codex 的 rollout 是严格线性的。「回到第 6 步」必然产生一个新 thread（新文件或新引用），你无法在一个文件里同时看到两条支线，也没有 Pi 那样的树视图。血缘只能靠 `forked_from_id` / `history_base` 反查，UI 上要自己拼。
- **复杂度不低**。为了让线性文件支持分叉、压缩、归档、跨文件引用，代价是一个十几个模块的 crate（约 14000 行含测试）：ordinal、字节偏移、引用索引、维护锁、backfill、read-repair。这是把「产品级运维需求」做扎实的价格，小项目照抄没有意义。
- **SQLite 有启动开销**。backfill 未完成时最多等 30 秒，然后退化到文件扫描；第一次在一个有几千个历史会话的机器上启动，会有可感知的等待。
- **`Referenced` fork 引入耦合**。父 rollout 被引用期间不能被压缩/删除，需要引用计数配合，这是 `Copied` 没有的运维负担。
- **按日期分目录**：「列出本项目的所有会话」不是一个 O(1) 查询，得靠 DB 索引或全扫过滤。

## 4. LangChain v1 / LangGraph 的做法

### 4.1 一句话概括

**根本不存消息列表，存的是每个 superstep 之后的完整图状态快照**（Checkpoint）；用 `thread_id` / `checkpoint_ns` / `checkpoint_id` 三级寻址；额外持久化 pending writes 用于崩溃后不重复执行已完成的节点；时间旅行 = `get_state_history()` 列出所有快照 + `update_state()` 从任一点派生新分支；整个 checkpointer 是可插拔接口，内存/SQLite/Postgres 各一份实现。

### 4.2 机制拆解

**范式差异先说清楚**。Pi 和 Codex 存的是「对话发生了什么」，LangGraph 存的是「图的状态是什么」。这不是同一件事的两种写法，而是两种抽象：

- 消息列表是**领域特定**的。它假设你在做一个聊天型 agent。
- 图状态是**领域无关**的。channel 里可以是消息列表，也可以是一个计数器、一份检索结果、一个自定义 dataclass。LangGraph 不关心。

代价是 LangGraph 无法提供「Pi 的 `/tree` 里显示每条 user 消息」这种开箱体验——它不知道你的 state 里哪个字段是「用户说的话」。收益是同一套持久化机制能给任意工作流用。这就是「框架 vs 产品」这条轴在本章的具体投影。

**Checkpoint 的结构**：

`libs/checkpoint/langgraph/checkpoint/base/__init__.py:92`

```python
class Checkpoint(TypedDict):
    """State snapshot at a given point in time."""

    v: int
    """The version of the checkpoint format. Currently `1`."""
    id: str
    """The ID of the checkpoint.

    This is both unique and monotonically increasing, so can be used for sorting
    checkpoints from first to last."""
    ts: str
    """The timestamp of the checkpoint in ISO 8601 format."""
    channel_values: dict[str, Any]
    """The values of the channels at the time of the checkpoint."""
    channel_versions: ChannelVersions
    """The versions of the channels at the time of the checkpoint.

    The keys are channel names and the values are monotonically increasing
    version strings for each channel."""
    versions_seen: dict[str, ChannelVersions]
    """Map from node ID to map from channel name to version seen.

    Used to determine which nodes to execute next."""
    updated_channels: list[str] | None
```

三个字段撑起了整个恢复语义：

- `channel_values` = 数据本身。
- `channel_versions` = 每个 channel 当前的版本号（单调递增）。
- `versions_seen` = 每个节点「上次看到的各 channel 版本」。

**恢复时不需要知道「刚才跑到哪个节点了」**——把 `channel_versions` 和 `versions_seen` 一比，谁没跟上谁就该跑。这是 Pregel 模型的核心，也是为什么快照能做到完全自包含：状态里已经编码了「下一步该干什么」，不需要额外的程序计数器。

`id` 用 `uuid6(clock_seq=step)` 生成（`pregel/_checkpoint.py:210`），既唯一又按时间单调，所以能直接当排序键用。

**元数据与三级命名**：

`source` 这四个值本身就是本章主题的完整枚举：正常执行（loop）、外部输入（input）、人工改状态（update）、复制派生（fork）。翻一个 thread 的历史，从 `source` 就能读出「哪几步是人插手的」。

寻址是三级：

- `thread_id`：一条会话/一个工作流实例。
- `checkpoint_ns`：命名空间，用于子图（subgraph）。父图和子图的 checkpoint 存在同一个 thread 下但不同 ns。`get_state_history` 里那段 `recast_checkpoint_ns` + `get_subgraphs` 的逻辑（`pregel/main.py:1499`）就是把请求路由到对应子图。
- `checkpoint_id`：具体某一步。

**pending writes：另外两家都没有的东西**。这是 LangGraph 持久化设计里最值得抄的一条。

场景：一个 superstep 里有三个节点并行跑。节点 A 和 B 完成了，C 跑到一半进程被 kill。重启之后怎么办？

- 如果只存 checkpoint（superstep 之间才存），那这个 superstep 整体没提交，A、B、C 全部重跑。**A 和 B 如果有副作用（发了邮件、调了付费 API、改了文件），就会重复执行。**
- LangGraph 的做法：节点一完成就把它的输出（writes）单独持久化，挂在**当前** checkpoint 上：

`libs/checkpoint/langgraph/checkpoint/base/__init__.py:300`


重启后 `get_tuple()` 连同 `pending_writes` 一起返回（`CheckpointTuple` 的第五个字段），循环在准备任务时把已完成任务的结果直接贴回去，不再执行：

`libs/langgraph/langgraph/pregel/_loop.py:661`


`writes` 表的主键 `(thread_id, ns, checkpoint_id, task_id, idx)` 保证了幂等重放。这把持久化的粒度从「superstep 之间」细化到了「单个节点完成之时」，代价是每个节点完成都要写一次库。

对比一下：Pi 和 Codex 都是「每条消息/条目落一次盘」，它们的最小恢复单位就是消息；一个工具执行到一半崩溃，重启后那次工具调用整个丢失（Codex 会补 `<turn_aborted>` 标记让历史合法，但不会保留半截结果）。LangGraph 是唯一显式建模「任务级已完成写入」的。

**持久化时机可调**：

`libs/langgraph/langgraph/types.py:87`

```python

```

`pregel/main.py:2709` 的文档：

- `"sync"`：下一步开始前同步持久化（最安全、最慢）；
- `"async"`：下一步执行的同时异步持久化（默认）；
- `"exit"`：只在图退出时持久化（最快，崩溃全丢）。

`async` 模式下，`_put_checkpoint` 会把上一次的 future 传给下一次，强制 checkpointer 按顺序收到 checkpoint（`_loop.py:1200` 附近的 `_put_checkpoint_fut`）——异步但不乱序。这个「三档耐久度」是框架该有的样子：让使用者按自己的副作用成本选，而不是替他决定。

**时间旅行**。两步。第一步，列出历史：

第二步，从任一点派生。直接拿某个历史 snapshot 的 config（含 `checkpoint_id`）去 `invoke`，就是从那一点重跑；如果还想顺便改状态，用 `update_state()`：

`as_node` 是关键参数：你写进去的值会被当作「某个节点的输出」走一遍正常的 channel reducer 逻辑。如果那个 channel 是 `add_messages`，你的值会被 append 而不是覆盖——**人工修改和节点输出走完全相同的路径**，不存在两套语义。

**可插拔**。`BaseCheckpointSaver` 是纯抽象类，核心接口只有六个：`get_tuple` / `list` / `put` / `put_writes` / `delete_thread` / `delete_for_runs`，外加同步异步双份。官方实现有内存（`langgraph/checkpoint/memory`）、SQLite（`checkpoint-sqlite`）、Postgres（`checkpoint-postgres`），还有一个 `checkpoint-conformance` 包专门跑一致性测试套件——想自己写一个 Redis/DynamoDB checkpointer，把这套测试跑过就行。

在 LangChain v1 侧，这一切通过 `create_agent` 的一个参数暴露：

### 4.3 代价与适用边界

- **不自带存储位置**。LangGraph 不会在你的家目录建 `sessions/`，不给你 `--resume` 命令，不给你会话选择器。thread_id 从哪来、DB 部署在哪、怎么列出「我的会话」——全是使用者的事。这对做产品的人是纯粹的工作量转移；对做平台的人是必需的自由度。
- **快照体积**。每个 superstep 存一份完整 `channel_values`。一个 100 轮的 agent 会话，消息列表会被序列化 100 遍，第 100 份里含着前 99 轮的全部内容。这是 O(n²) 的存储。官方的缓解是 `DeltaChannel`（beta）：非快照步只在 `channel_values` 里放一个哨兵，实际增量存进 `writes` 表，读取时沿 parent 链回溯累加，每 `snapshot_frequency` 次才写一次完整 blob。但从 `prune` / `copy_thread` / `delete_for_runs` 那几段长得吓人的警告注释就能看出，这个优化把「删除历史」变成了一件危险操作——删掉中间的 checkpoint 可能切断 delta 重建链，而且**不报错，只是静默地重建成空**。
- **序列化约束**。所有进 state 的东西必须能被 serde 处理（默认 `JsonPlusSerializer`）。往 state 里塞一个数据库连接或文件句柄，会在持久化时炸。
- **人类可读性差**。checkpoint 是 BLOB。`jq` 一个 rollout 文件就能看懂 Codex 的会话；看 LangGraph 的 checkpoint 得先反序列化。审计友好度上明显不如前两家。
- **没有内建的「分支摘要」概念**。fork 之后被放弃的那一支，框架不会帮你总结——它不知道你的 state 语义。

## 5. 三方横向对比

| 维度 | Pi | Codex | LangChain v1 / LangGraph |
|---|---|---|---|
| **存储单元** | session entry（message / 状态变更 / 压缩 / 摘要 / 标签 / 扩展数据，9 种） | rollout item（ResponseItem / EventMsg / Compacted / TurnContext / WorldState / SessionMeta，落盘清单由 `policy.rs` 穷尽枚举） | Checkpoint = 一个 superstep 后的**完整** `channel_values` + `channel_versions` + `versions_seen`；外加任务级 pending writes |
| **格式与位置** | JSONL，`~/.pi/agent/sessions/--<cwd 编码>--/<ts>_<uuid>.jsonl`；每 session 一个文件 | JSONL，`~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<thread_id>.jsonl`；冷文件 zstd 压成 `.jsonl.zst` | 由 checkpointer 决定：内存 dict / SQLite 两表 / Postgres；BLOB + serde |
| **索引方式** | 目录名即 cwd；打开文件全量读入内存建 `byId` Map；SQLite 后端另有 `branch_entries` / `branch_tips` 派生缓存 | 三层：文件名含时间戳+id（可直接排序）→ `session_index.jsonl`（名字，append-only + 反向扫描）→ SQLite 状态库（backfill 生成，可整个删掉重建，查不到就落回文件扫描 + read-repair） | SQL 复合主键 `(thread_id, checkpoint_ns, checkpoint_id)`；`list()` 按 checkpoint_id 倒序 |
| **恢复粒度** | 任意 entry（消息级）。`buildContextEntries()` 沿 leaf→root 走一遍，按压缩点做投影 | 任意已落盘的 item；mid-turn 恢复会补 `<turn_aborted>` 使历史合法 | 任意 checkpoint（superstep 级），**再往下**还有 pending writes 到任务级 |
| **分支模型** | **单文件内一棵树**（`id`/`parentId` + active leaf）。三种命令：`/tree` 原地导航（可带分支摘要）、`/fork` 从 user 消息开新文件、`/clone` 复制当前分支到新文件 | **线性文件，跨文件分叉**。切点 `ForkSnapshot`（第 n 条 user 消息前 / 当前中断点）× 存储 `ForkPersistence`（`Copied` 复制前缀 / `Referenced` 用 `HistoryPosition` 引用父文件前缀）；血缘靠 `forked_from_id` + `RolloutReferenceIndex` | **DB 内一棵树**（`parent_checkpoint_id`）。`update_state()` 从任一点派生 `source="update"`；`as_node="__copy__"` 产生 `source="fork"` 的兄弟节点 |
| **崩溃恢复** | append-only，最坏丢最后一行（解析器跳过坏行）。但首条 assistant 到达前完全不落盘 → 第一个 turn 崩溃全丢 | 后台 writer 任务 + 可等待 `flush`/`persist`；反向扫描器容忍末尾残行；fork 前强制 flush | **唯一显式建模「节点级已完成写入」**：`put_writes` 把每个完成任务的输出单独落库，重启后已完成的任务不重跑（`_reapply_writes_to_succeeded_nodes`）。耐久度三档 `sync`/`async`/`exit` 可选 |
| **可插拔性** | 默认 JSONL 后端硬编码在 `SessionManager`；另有独立包 `session-backends/sqlite-node` 提供 SQLite 实现 | 不可插拔。JSONL 是唯一真相，SQLite 只是索引层；`thread-store` 抽象了本地/内存两种实现但不面向用户 | **核心设计点**。`BaseCheckpointSaver` 六个方法即可实现自定义后端，官方提供内存/SQLite/Postgres + 一个 conformance 测试包 |
| **跨设备同步** | 无内建同步。`/share` 上传私有 GitHub gist（只读 HTML 分享，非同步）；`--session-dir` 可指向共享目录，但无锁 | 无内建同步（本地 `~/.codex`）。远端能力走 app-server / cloud-tasks 等独立组件，不在 rollout crate 内 | 天然支持：换成 Postgres checkpointer 即多机共享，`thread_id` 就是全局键。这是「框架」定位的直接红利 |
| **并发写保护** | 默认 JSONL 后端**无锁**（源码中无 flock/lock）；SQLite 后端有 `writer_leases` 表 + fencing token | 进程内 mpsc 单写者；维护类操作有 `rollout-maintenance.lock`（文件锁）+ 压缩 run marker 限流；per-thread writer 锁 | 交给底层 DB 事务；`writes` 表主键保证重放幂等 |
| **体积治理** | 无。放弃的分支永久保留，无压缩无归档，删除靠用户手动（优先 `trash`） | 三层：7 天以上冷文件 zstd 压缩（透明读、写前解压）、`archive`/`unarchive` 目录搬移、`delete` | `prune(strategy="keep_latest"/"delete")`、`delete_thread`、`delete_for_runs`；但用了 `DeltaChannel` 时删除会切断重建链且不报错 |
| **人类可读性** | 高。JSONL 直接 `jq`，字段语义清晰 | 高。第一行即全部元数据，`jq -C .` 是官方推荐用法 | 低。checkpoint 是序列化 BLOB |

有几条结论值得单独拎出来：

**「树」出现在三家，但在三个不同的层次上。** Pi 的树节点是消息，在文件内；LangGraph 的树节点是状态快照，在数据库里；Codex 干脆不在单个存储单元内建树，而是在**文件之间**建血缘（`forked_from_id` / `history_base`）。从用户视角看，Pi 的 `/tree` 和 LangGraph 的 `get_state_history()` + `update_state()` 在做**同一件事**，但一个是消息树导航，一个是状态图快照派生。

**只有 LangGraph 认真处理了「执行到一半崩溃」。** Pi 和 Codex 的最小持久化单位是「一条已完成的消息」，所以「工具跑了一半进程死了」这件事在它们的模型里是不可恢复的（Codex 至少保证恢复出来的历史在协议层合法）。这个差异的根源是定位：CLI agent 的 turn 通常几十秒，崩了重来成本可接受；工作流框架的一个节点可能跑十分钟并且有外部副作用，重跑是不可接受的。

**索引策略反映了默认查询。** Pi 按 cwd 分目录（默认查询：本项目的会话）；Codex 按日期分目录 + SQLite 索引（默认查询：最近的会话，跨项目）；LangGraph 交给 SQL（默认查询：这个 thread 的历史）。

## 6. 可以拿走的工程经验

**1. 把「能回到第 N 步」当成一等公民，而不是调试功能。**
Pi 的实现值得直接照抄：选中一条历史 user 消息 → leaf 退到它的父节点 → 原文本回到编辑器 → 用户改完重发就是新分支。全部代价只是「entry 加两个字段 `id`/`parentId`」和「一个 leaf 指针」。适用条件：你的会话是可分叉的（对话/工作流），不是严格串行的事务流。

**2. 存储清单要显式且被编译器/类型系统守住。**
Codex 的 `policy.rs` 用穷尽 match 强迫每种事件回答「要不要落盘」。这不是洁癖——新增一个事件类型时忘记决定它是否持久化，是最典型的「半年后才发现 resume 少东西」的 bug 来源。TypeScript 里用 discriminated union + `switch` 加 `never` 兜底能达到同样效果。

**3. 反向扫描 append-only 文件，是拿「最新状态」的正确姿势。**
只要你的元数据更新是 append-only + 后写覆盖先写（会话名、标签、当前模型……），就不需要为了「读最新值」而扫全文。从尾部 seek + 逐块回溯找 `\n`，几十行代码，把 O(文件大小) 变成 O(1)。三个必备细节：单条记录大小上限（跳过巨型 blob）、解析失败不中断（容忍末尾残行）、可指定逻辑末尾字节（用于扫描冻结前缀）。

**4. 如果一个节点/工具有外部副作用，就要把「已完成」这件事单独持久化。**
LangGraph 的 `put_writes` + `(thread_id, ns, checkpoint_id, task_id, idx)` 主键是最小可用方案：任务一完成就写一条，恢复时把结果贴回去而不是重跑。判断标准很简单——**如果重跑一次会多发一封邮件/多花一次 API 费用/多改一次文件，就必须做**；如果节点是纯函数，`sync`/`exit` 之外的复杂度都是浪费。

**5. 索引和真相分开，索引必须能被整个删掉重建。**
Codex 的 SQLite 状态库是这条的范本：backfill 从 JSONL 生成，查询未命中就落回文件扫描并 read-repair，DB 文件删了下次启动重建。这样你永远不用回答「DB 和文件不一致时以谁为准」——答案永远是文件。适用条件：真相数据本身可以被完整扫描（哪怕慢）。

**6. 分支切换时，别默认丢掉被放弃的那条路。**
Pi 的 `branch_summary` 把「方案 A 为什么行不通」带到新分支上，避免 agent 重蹈覆辙。实现只需要：求两条路径的最近公共祖先 → 把旧 leaf 到公共祖先这一段丢给 LLM 总结 → 作为一条特殊 entry 挂在新位置。但要把它做成**可选**（多一次 LLM 调用是真金白银），并提供一个「别再问我了」的设置。

**7. 体积治理要在 day 1 就留好接口，哪怕先不实现。**
Codex 的三件套值得参考：冷数据压缩（阈值 7 天 + 透明读取 + 写前解压）、归档（就是 `rename` 到另一个目录 + 打标记，零风险）、删除（能进回收站就别 `unlink`——那可能是几小时不可复现的工作）。Pi 目前三件都没做，会话目录只增不减。

**8. 「临时会话」和「分叉」是正交的，组合起来会白送你一个功能。**
Codex 的 `/side`「start a side conversation in an ephemeral fork」= `--ephemeral`（不落盘）+ fork（从当前状态派生）。两个独立能力，零额外代码，得到「问个闲事不污染主线」这个高频需求。设计能力时优先做正交的原语，而不是直接做组合出来的功能。

## 8. 第四个样本：Grok Build

> 调研时间 2026-08-06，`xai-org/grok-build` commit `a5589e9`；全项目背景见 [17 番外](./17-番外-GrokBuild全项目速览.md)。本节只讲持久化与分支维度。

**一句话定位**：对照本章的三分法——Pi 消息树、Codex 跨文件引用、LangGraph 状态快照——Grok Build 是**双日志 + 目录复制**的第四种：一个会话目录里同时养两个 JSONL，分支靠整目录拷贝这个最笨也最稳的办法，时间旅行则按场景在「投影截断」和「事件重放」之间切换。

**双 JSONL，分工明确**（目录 `~/.grok/sessions/{url_encoded_cwd}/{session_id}/`，`storage/jsonl/mod.rs:26`）：

- `chat_history.jsonl` —— `ConversationItem` 流，**可替换投影**：压缩和 rewind 时被 `ReplaceChatHistory` 整体重写，喂模型用；
- `updates.jsonl` —— ACP SessionUpdate 事件流，**只追加**：rewind 不删它，只追加 `RewindMarker`（`rewind.rs:469-471`），喂 UI 重放历史用。

即：**Pi 的「append-only 事件日志 + 投影」和 Codex 的「内存权威 + 写后落盘」在同一个目录里各占一个文件**。平时读写走投影快路径；只有当 rewind 目标点落在压缩边界之前、`chat_history.jsonl` 已无原文时，才动用 Pi 式重放——`replay_to_prompt` 流式重放 `updates.jsonl` + compaction checkpoint 文件重建对话（`session/helpers/replay.rs:1-31`），遇 `RewindMarker` 把已积累的 prompts 截回目标。

**耐久度是显式两档**：`AppendDurability::{Buffered, Durable}`（jsonl/mod.rs:22-25），普通 chat append 走 Buffered（**不 fsync**），只有 cwd-switch 等关键点走 Durable（`sync_all` + fsync 父目录）；需要屏障时用 `FlushAndAck`（persistence.rs:397-402），用户 prompt 要过两级 ack 才回 client 的 `persist_ack`。对照本章第 5 节崩溃恢复行：比 Pi 的每条同步 append 弱、比 LangGraph 的 `sync/async/exit` 三档少一档，与 Codex 的后台 writer + 可等待 flush 同型。

**torn-tail 自愈是写侧方案**：append 前检查文件最后一个字节，非 `\n` 则先补一个把上次的残行封死成单条坏行，读端宽容跳过（storage/jsonl/mod.rs:257-330）——注释里明写这个 bug 曾经 "bricked session resume"。对照 Codex 的**读侧**方案（反向扫描器容忍残行）：一个在写入时消毒，一个在读取时容错，殊途同归。

**分支 = 目录复制**（`session/fork.rs:66-163`）：`fork_session` 把整个会话目录 `copy_session_data_sync` 到新 UUIDv7 id，`summary.parent_session_id`（fork.rs:50,97）指回源，支持 `target_prompt_index` 在历史任意点截断开叉、顺便换模型。没有 Pi 的树内 `parentId`，没有 Codex 的 `(thread_id, ordinal, byte_offset)` 字节区间引用——空间成本最高（全量拷贝），但**零悬挂引用问题**：Codex 要处理父文件被删/截断，Grok 的 fork 天生自包含。

**Rewind 是四个样本中唯一把工作区文件也纳入回滚的**：每个 prompt 都是 checkpoint（`rewind.rs:26-28`），三模式 `All / ConversationOnly / FilesOnly`——对话回滚发 `TruncateToPromptIndex` 给 chat actor 按第 N 个 User item 截断（`xai-chat-state/src/actor/queries.rs:47-81`），文件回滚用 FileStateTracker 的 before/after 快照，`force=false` 是带外部改动冲突检测的 dry-run 预览。Pi/Codex/LangGraph 回退的都只是对话或图状态，agent 改过的文件要靠 git 自己收拾；Grok 把「回到第 6 步」做成了对话和文件系统的联动回滚。

**SQLite 只是全文搜索索引**，非真相源（search_fts.rs:23）——与 Codex 的 state_db 同一哲学：「SQLite 是可以整个删掉重建的缓存，JSONL 是唯一真相」，本章第 3 节夸过的克制设计在第四个样本上再次出现，这大概可以升格为行业共识了。

**Resume 路径**：`MvpAgent::load_session` → 解析 `chat_history.jsonl` 播种 ChatStateActor（`spawn_with_pruning`），`updates.jsonl` 重放给客户端渲染 UI，dangling tool call 修复由 `ChatState::new()` 写边界自动完成（`session_setup.rs:640-877`、spawn.rs:552-574）。

**本节未确认**：`rewind_points.jsonl` 的文件快照是全量拷贝还是 diff，未读实现；fork 后父目录被删除时 `parent_session_id` 的悬挂语义（只影响 resume 去重，推断无损），未验证；两个 JSONL 之间不一致时（Buffered 落后于事件流）resume 的仲裁逻辑，未逐行确认。
