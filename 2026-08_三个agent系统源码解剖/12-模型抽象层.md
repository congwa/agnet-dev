## 0. 先搞清楚：这是个什么东西

假设你写了一个 agent 循环：把对话历史发给模型，模型返回文本或者工具调用，你执行工具，把结果塞回历史，再发一次。这个循环里唯一跟「厂商」相关的部分，就是「把历史发出去、把响应读回来」这一小段。听起来只要封装一个 `callModel(messages, tools) -> response` 就完事了。

实际不是。这一小段里藏着四类彼此不兼容的东西：

**请求体的形状不同。** 一家把系统提示放在 `messages` 数组里当 `role: "system"`，另一家有独立的 `system` 顶层字段；一家的多模态内容是 `{type: "image_url", image_url: {url: "data:..."}}`，另一家是 `{type: "image", source: {type: "base64", media_type, data}}`；工具定义有的叫 `functions`，有的叫 `tools`，参数 schema 有的要求 `strict: true` 有的会因为这个字段直接 400。

**思考链（reasoning）是一等公民而且不透明。** 现在主流推理模型返回的不只是文本，还有一段「思考」。麻烦的地方是：**很多厂商的思考内容必须原样回传给下一轮**，否则模型会拒绝或者行为退化。有的回传的是明文加一个签名字符串，有的回传的是一整块加密 blob，有的把它挂在工具调用上而不是消息上。抽象层如果按「只保留文本」的最小公分母来做，多轮推理就直接坏掉。

**流式事件的粒度不同。** 有的协议是「内容块开始 / 增量 / 结束」的结构化事件流，有的是每个 chunk 里塞一个 delta 对象让你自己拼装 index，有的干脆走的是二进制帧。工具调用的参数在流里往往是一段一段的 JSON 字符串碎片，需要按索引累积后才能解析。

**用量与计费口径不同。** `input_tokens` 到底含不含缓存命中的部分？`output_tokens` 含不含思考 token？缓存写入是按输入价还是另有单价？有没有 `total_tokens` 这个字段？答案每家都不一样，而 harness 需要一个统一的数字来做上下文压缩决策和成本显示。

所以「模型抽象层」这件事的真正内容是：**定义一套内部的消息 / 工具调用 / 流式事件 / 用量类型，然后为每种线上协议（wire protocol）写一个双向翻译器**，再加上一层「哪些模型存在、怎么认证、默认用哪个」的目录管理。

## 1. 为什么这件事很难

**张力一：抽象做薄抹不平，做厚丢特性。** 最小公分母抽象（只有文本 + 工具调用）能跑通所有厂商，但会丢掉 Anthropic 的 prompt cache 断点标记、OpenAI 的 reasoning summary 与 encrypted reasoning、Google 的 thought signature、OpenRouter 的上游路由偏好——而这些恰好是省钱和提质的关键。反过来，如果抽象层的类型里塞满各家专属字段，它就不再是抽象层，只是一个把所有 SDK 并集起来的大杂烩，新增一家厂商要改核心类型。

**张力二：能力探测没有标准答案。** 「这个模型支持工具调用吗 / 支持图片输入吗 / 支持 128K 上下文吗 / 支持 structured output 吗」——没有任何厂商提供一个可靠的、机读的能力查询接口。可选路径只有三条：硬编码一张表（会过期）、运行时探测（要浪费真实请求，且失败模式难区分）、从 base URL 猜（对自建代理必然猜错）。而且能力是**模型级**而非 provider 级的：同一个 Anthropic 账号下，Haiku 和 Opus 的能力集就不同。

**张力三：不透明状态必须端到端穿透。** reasoning 签名、加密思考块、response id、缓存 key，这些字段 harness 自己完全不理解，但必须存进会话历史、跨进程重启后还原、并在下一轮原样发回。这意味着抽象层的消息类型必须有「我不懂但我保管」的槽位，而会话持久化格式也得跟着带上它们。

**张力四：认证有两条完全不同的路。** API key 是无状态的：读环境变量、拼一个 header，完事。订阅登录（Claude Pro/Max、ChatGPT、GitHub Copilot）是有状态的 OAuth：要跑浏览器授权、存 refresh token、在 access token 过期时刷新，而且**刷新必须串行化**——并发的两个请求同时发现 token 过期然后各刷各的，会导致其中一个 refresh token 被作废。

**张力五：模型目录会过期。** 编译进二进制的模型列表，在模型发布节奏是「每两个月一代」的今天，意味着用户升级 CLI 才能用上新模型。要么从远端拉，要么接受滞后。

## 2. Pi 的做法

### 2.1 一句话概括

Pi 把整个模型世界压成 **10 种 wire API × 一套统一的 `Message` / 事件流类型**，用 85 个 provider 文件承载「身份 + 目录 + 认证」，用 per-model 的 `compat` 标志位把厂商特性穿透回去——**模型是可替换的商品，harness 不为任何一家做特殊设计**。

### 2.2 机制拆解

Pi 的抽象层是明确的**两层**结构，这一点比另外两个项目都清晰：

- `packages/ai/src/api/`：**wire 协议适配器**，一共 10 个 —— `anthropic-messages`、`openai-responses`、`openai-completions`、`azure-openai-responses`、`openai-codex-responses`、`google-generative-ai`、`google-vertex`、`bedrock-converse-stream`、`mistral-conversations`、`pi-messages`。这些是真正干脏活的地方，`anthropic-messages.ts` 1351 行、`openai-completions.ts` 1575 行、`openai-codex-responses.ts` 1650 行，10 个适配器合计约 7700 行。
- `packages/ai/src/providers/`：**provider 定义**，85 个文件（每个 provider 一个 `.ts` 描述身份/base URL/认证，一个 `.models.ts` 挂模型目录）。provider 只负责「我是谁、我的模型有哪些、怎么认证」，然后指向一个 wire 适配器。

这个分层的意义：Groq、Cerebras、Together、Fireworks、DeepSeek、xAI 这一堆 provider 全都复用 `openai-completions` 适配器，新增一家只要写 30 行 provider 定义 + 一份模型目录，不碰协议代码。

统一类型全在 `types.ts`（820 行）：`Message` 是 `UserMessage | AssistantMessage | ToolResultMessage` 三选一，`AssistantMessage.content` 是 `(TextContent | ThinkingContent | ToolCall)[]`。不透明状态有专门槽位——`TextContent.textSignature`、`ThinkingContent.thinkingSignature`、`ThinkingContent.redacted`、`ToolCall.thoughtSignature`（注释直接写了 `Google-specific`）。

**能力探测**走的是「生成期建表 + 类型级 compat 覆盖」。`packages/ai/src/providers/*.models.ts` 全是自动生成的八行文件，数据来自构建脚本从 `https://models.dev/api.json` 抓取（`scripts/generate-models.ts:1193`）再叠加人工修正。运行期的能力差异则由 `Model.compat` 表达，而且这个字段是**按 API 类型条件化**的：`anthropic-messages` 的模型只能填 `AnthropicMessagesCompat`，`openai-responses` 的只能填 `OpenAIResponsesCompat`。

**模型目录刷新**：静态目录之外，`Provider.refreshModels()` 允许 provider 在运行时拉取动态列表（OpenRouter、NVIDIA、Vercel AI Gateway 等走这条路），结果落盘到 `~/.pi/models-store.json`，条目带 `etag` / `lastModified` / `checkedAt`，下次请求用 `If-None-Match` 回源。

**认证两条路**：`ProviderAuth` 同时可以有 `apiKey` 和 `oauth`。OAuth 实现放在 `packages/ai/src/auth/oauth/`：`anthropic.ts`（Claude Pro/Max）、`openai-codex.ts`（ChatGPT Codex）、`github-copilot.ts`、`kimi-coding.ts`、`openrouter.ts`、`xai.ts`、`radius.ts`，外加通用的 `device-code.ts` 和 `pkce.ts`。刷新的串行化由 `CredentialStore.modify()` 保证——注释写明「`Models.getAuth()` 在 `modify` 内部执行 OAuth 刷新，因此并发请求不会重复刷新一个已轮换的 token」。

扩展点 `pi.registerProvider()` 有 774 行专门文档（`packages/coding-agent/docs/custom-provider.md`），支持两种粒度：传一个完整的 `createProvider(...)` 结果（可自定义认证、过滤、刷新、乃至整个流式实现），或者传轻量的 provider-config 覆盖已有 provider 的 baseUrl。文档明确说明了组合顺序：「pi 把 `models.json` 覆盖叠在已注册的原生 provider 之上」。

### 2.4 代价与适用边界

- **维护成本是真金白银的。** 10 个 wire 适配器 7700 行，85 个 provider 文件，加上一个从 models.dev 抓数据的生成脚本和它的人工修正表（`generate-models.ts` 里有多处「models.dev 还没更新，先用权威值」的补丁注释）。这套东西必须持续跟随每一家厂商的 API 变更。
- **`compat` 标志位会无限增长。** 每发现一个撒谎的兼容层就加一个布尔字段，这是个只增不减的集合，而且默认值语义（「Default: true」还是「auto-detected from URL」）散落在注释里，对自建代理的用户不友好。
- **抹平意味着不押注。** Pi 不能围绕某一家的独有能力做深度产品设计（比如把某家的服务端会话状态当作核心机制），因为那会破坏「换个 provider 照样能跑」的承诺。

## 3. Codex 的做法

### 3.1 一句话概括

Codex 把协议抽象层**砍到只剩一个变体**——`WireApi` 枚举里只有 `Responses`，Chat Completions 支持已被完整移除；模型目录不再硬编码，改由服务端下发；连本地跑的 Ollama / LM Studio 也被要求提供 Responses 端点。

### 3.2 机制拆解

这是本章最有信息量的一处源码。Codex 的 `WireApi` 是一个只有单个变体的枚举——在 Rust 里，单变体枚举完全等价于一个空 struct，它存在的唯一理由就是**保留 config 反序列化时报错的位置**。

内置 provider 只有 4 个：`openai`、`amazon-bedrock`、`ollama`、`lmstudio`，源码注释直接给出了理由（见 2.3 引用）。其中 Bedrock 走的也不是 AWS Converse API，而是 `https://bedrock-mantle.us-east-1.api.aws/openai/v1` —— 一个 OpenAI 兼容端点。也就是说 Codex 眼中的 Bedrock 是「另一个 Responses 端点」，不是另一种协议。

**模型目录**在这一代已经从「硬编码 presets」迁移到「服务端下发」。`model_presets.rs` 整个文件只剩 5 行，注释写明「Hardcoded model presets were removed; model listings are now derived from the active catalog」。取而代之的是 `models-manager` crate：`OpenAiModelsManager` 从 `/models` 端点拉目录，`FileModelsCache` 以 **300 秒 TTL** 缓存到 `codex_home`，带 ETag 与 client version 校验（版本不匹配直接判定缓存失效）；编译进二进制的 `models.json` 只是 `bundled_models_response()` 这个 fallback。刷新策略是三态的 `RefreshStrategy { Online, Offline, OnlineIfUncached }`。

模型能力在 Codex 里同样是结构化的，但**字段是 Codex 私有的、面向自家 harness 的**：`models.json` 里每个模型带 `prefer_websockets`、`apply_patch_tool_type`、`web_search_tool_type`、`tool_mode: "code_mode_only"`、`multi_agent_version: "v2"`、`use_responses_lite`、`include_skills_usage_instructions`、`truncation_policy`、`comp_hash`、`supported_reasoning_levels`（6 档，含 `ultra`：「Maximum reasoning with automatic task delegation」）。这些不是「模型的通用能力」，而是「这个模型在 Codex 里应该开哪些 harness 特性」——模型与 harness 是**一体设计**的。

**认证**只有一套枚举 `AuthMode`，7 个变体全部围绕 OpenAI 生态：`ApiKey`、`Chatgpt`、`ChatgptAuthTokens`、`Headers`、`AgentIdentity`、`PersonalAccessToken`、`BedrockApiKey`。其中 4 种被 `uses_codex_backend()` 判定为「走 Codex 服务而非直连模型 API」。

**传输层**：Responses over WebSocket 优先，HTTP SSE 是降级路径，而且降级是**会话级、单向、不可回退**的。

`disable_websockets.swap(true, ...)` 是一个 `AtomicBool`，一旦置位整个 session 都不再尝试 WebSocket。函数上方的文档注释写着「Permanently disables WebSockets for this Codex session」。这个决定的合理性在于：WebSocket 失败通常源于企业代理/防火墙这类不会在会话中途改变的环境因素，反复重试只是浪费；代价是一次偶发的网络抖动会让整个会话丢掉 WebSocket 的延迟优势。是否使用 WebSocket 由**两级**决定：provider 的 `supports_websockets`（内置 OpenAI provider 是 `true`，Bedrock 是 `false`）和模型目录里的 `prefer_websockets`。

### 3.4 代价与适用边界

- **接第三方模型基本不可行。** 除非对方提供 Responses 端点，否则无路可走。这不是「配置麻烦」，是协议层面的拒绝。用 Codex 的前提是接受 OpenAI 模型（或 Bedrock 上转售的 OpenAI 模型）。
- **目录服务端化把控制权交给了服务端。** 离线（`RefreshStrategy::Offline`）时只能吃 bundled fallback，且 fallback 的 `model_info.rs:139` 对未知 slug 只能造一个最小描述符并 `warn!("Unknown model {slug} is used. This will use fallback model metadata.")`——能力全靠猜。
- **模型与 harness 一体化让能力字段无法复用。** `include_skills_usage_instructions`、`comp_hash`、`multi_agent_version` 这类字段离开 Codex 就没有意义，别的项目抄不走。
- **换来的是什么**：整个 core 里没有任何「如果是 Anthropic 就……」的分支，请求构造、流式解析、重试、压缩全部只有一条代码路径。这是 Pi 的 7700 行适配器代码换不来的简洁。

## 4. LangChain v1 的做法

### 4.1 一句话概括

LangChain 不做 wire 协议适配——它定义一个抽象基类 `BaseChatModel`（两个抽象方法：`_generate` 和 `_llm_type`），把适配工作外包给 17 个独立发布的 partner 包，然后用一个**结构化的模型能力档案 `ModelProfile`** 让上层逻辑可以在不知道厂商的情况下做决策。

### 4.2 机制拆解

`BaseChatModel` 是 LangChain 的立身之本，`chat_models.py` 有 2700 余行，但真正要求 partner 实现的只有两个 `@abstractmethod`：`_generate()`（同步生成）和 `_llm_type`（标识串）。`_agenerate` / `_stream` / `_astream` 都有默认实现（`_agenerate` 默认是 `run_in_executor` 包 `_generate`）。基类自己承担的是 callback 分发、缓存、批处理、`bind_tools` / `with_structured_output` 的声明式包装、以及 rate limiter 挂载。

**能力档案是三者中唯一把「模型支持什么能力」结构化建模的东西**。`ModelProfile` 是一个 `total=False` 的 TypedDict，约 30 个字段，分五组：模型元数据（name/status/release_date/open_weights）、输入约束（max_input_tokens、image/pdf/audio/video_inputs、image_url_inputs、image_tool_message、pdf_tool_message）、输出约束（max_output_tokens、reasoning_output、reasoning_effort_levels、reasoning_effort_default、image/audio/video_outputs）、工具调用（tool_calling、tool_choice、tool_call_streaming）、结构化输出与其他（structured_output、attachment、temperature）。

数据来源是 **models.dev**（跟 Pi 一样），但流程不同：`libs/model-profiles/` 是一个独立的 CLI 工具包 `langchain-profiles`，maintainer 跑 `langchain-profiles refresh --provider anthropic --data-dir ./langchain_anthropic/data`，它下载 models.dev 数据、合并 `profile_augmentations.toml` 里的人工覆盖、生成 `_profiles.py`。覆盖文件长这样（Anthropic 的）：全局覆盖 `structured_output = false`、`pdf_inputs = true` 等，再按模型 id 逐个开洞（`[overrides."claude-sonnet-4-6"] structured_output = true` + `reasoning_effort_levels = ["low","medium","high","max"]`）。

`init_chat_model()` 提供字符串路由：`"anthropic:claude-sonnet-4-5"` 这种 `provider:model` 语法，或者从模型名前缀猜 provider。路由表 `_BUILTIN_PROVIDERS` 有 28 项，映射到「包名 + 类名 + 构造函数」三元组，**懒导入**（`functools.lru_cache` 包住 `_get_chat_model_creator`）。注意 28 个路由项 vs 仓库里 17 个 partner 目录——路由表覆盖的包有一部分（`langchain_aws`、`langchain_cohere`、`langchain_google_*`、`langchain_ibm`、`langchain_litellm`、`langchain_nvidia_ai_endpoints`、`langchain_together`、`langchain_upstage`、`langchain_baseten`、`langchain_meta`、`langchain_azure_ai`）住在独立仓库里。

**降级与限流是 middleware / 组件，不在抽象层里**：`ModelFallbackMiddleware`（按序换模型重试）、`ModelRetryMiddleware`（指数退避重试同一模型）、`InMemoryRateLimiter`（令牌桶，挂在 `BaseChatModel.rate_limiter` 上）。

When a caching middleware such as `AnthropicPromptCachingMiddleware` wraps this

### 4.4 代价与适用边界

- **抽象层不管 wire 协议，所以厂商特性只能走 `**kwargs`。** 可移植性由使用者负责，框架不保证换个模型还能跑。上面 `model_fallback.py` 的 doc 就是这个设计的直接后果。
- **能力档案是 Beta，数据可能过期或缺失。** `total=False` + `contextlib.suppress` + fallback 正则表 + Gemini 特判，四层兜底堆在一起，说明 profile 目前还不足以单独作为决策依据。
- **版本矩阵。** 17+ 个独立发布的 partner 包 × langchain-core 版本，`_warn_unknown_profile_keys` 的存在本身就是这个问题的证据。
- **换来的是什么**：LangChain 完全不需要跟着任何厂商的协议变更跑。Anthropic 改了 API，改的是 `langchain-anthropic` 的发版，`langchain-core` 一行不动。这是「框架」相对「产品」的结构性优势。

## 6. 可以拿走的工程经验

1. **把「provider 身份」和「wire 协议」拆成两层。** Pi 的 85 个 provider 文件对 10 个协议适配器是多对一：Groq、Cerebras、Together、Fireworks、DeepSeek 全部复用 `openai-completions`。新增一家只写 30 行身份定义。**适用条件**：你要接 5 家以上，且其中多数自称 OpenAI 兼容。只接 1-2 家时这一层是纯开销。

2. **给「兼容层的谎言」留标志位，并让它按协议类型强类型化。** `supportsCacheControlOnTools`、`supportsTemperature`、`supportsStrictMode` 这些字段的存在不是过度设计，是现实——自称兼容 Anthropic Messages 的端点不吃 tools 上的 `cache_control`，Claude Opus 4.7 拒绝非默认温度。Pi 用条件类型让 `anthropic-messages` 的模型填不进 OpenAI 的 compat 字段。**适用条件**：一旦你开始接第三方托管/代理端点，就必须做这个；直连一手 API 可以先不做。

3. **模型目录不要硬编码进二进制。** 三家给了三种成本梯度：Codex 的服务端下发 + 300s TTL（最新，但需要服务端配合且离线退化）、Pi 的构建期从 models.dev 生成 + 运行期可选刷新 + etag 落盘（折中）、LangChain 的随包发版（最省事，但滞后一个发版周期）。**适用条件**：你自己有服务端就学 Codex；没有就学 Pi 的「生成期抓公开数据源 + 人工修正表」——models.dev 这个开源项目同时被 Pi 和 LangChain 当作上游，可以直接用。

4. **「无全局默认模型」是个有效的产品立场，用类型系统钉住它。** `Record<KnownProvider, string>` 强制穷举 38 个 provider，新增 provider 不填默认就编译失败。这比「有个全局默认，其他 provider 各自 fallback」更诚实：不同 provider 的模型不可比，「本产品推荐 X」这个说法只在单一 provider 内成立。**适用条件**：多 provider 产品。

5. **不透明状态（reasoning 签名、加密思考块、thought signature）必须在消息类型里有显式槽位。** Pi 的 `thinkingSignature` / `textSignature` / `thoughtSignature` / `redacted` 四个字段，加上会话持久化一并保存，是多轮推理不退化的前提。**适用条件**：只要你用推理模型且会话超过一轮，这是必做项——而且要在设计消息 schema 的第一天就留位，事后补会牵动整个持久化格式。

6. **传输层降级要单向锁死并打点。** Codex 的 `disable_websockets.swap(true, Ordering::Relaxed)` + `codex.transport.fallback_to_http` 计数器：失败原因通常是不会中途改变的环境因素（企业代理、防火墙），反复重试只是浪费；但一定要打点，否则你不知道有多少比例的用户实际跑在降级路径上。**适用条件**：任何有主备传输的场景。

7. **能力档案有天花板，别指望它替代所有特判。** LangChain 的 `factory.py:559` 是最好的反面教材：profile 说 `structured_output: true`，但「结构化输出 + 工具调用同时用」这个组合约束表达不了，于是旁边挂着一个 Gemini 版本号的硬编码 if。**结论**：能力档案适合表达一维事实（上下文窗口、支不支持图片），不适合表达能力之间的交互约束；后者老老实实特判并写清注释。

## 8. 第四个样本：Grok Build

> 调研时间 2026-08-06，`xai-org/grok-build` commit `a5589e9`；全项目背景见 [17 番外](./17-番外-GrokBuild全项目速览.md)。本节只讲模型抽象维度。

**一句话定位**：本章讲了三种付法——Pi 养 10 套适配器抹平一切、Codex 砍到单变体锁死自家、LangChain 外包给生态包。Grok Build 是第四种：**fork 一个现成 SDK，单 client 说三种协议方言**——而它跟 Codex 的对比是全系列最工整的一组镜像。

**Wire 层 = fork 的 async-openai**。根 Cargo.toml:3-4 用 `[patch.crates-io]` 把 `async-openai` 整个替换成自家 fork（`our-forks/async-openai`），xAI 专有字段靠请求体注入/剥离补丁（`sampler/src/client.rs:1346` "Inject xAI-specific fields not in async-openai's CreateResponse type"）。既不是 Pi 的自写适配器，也不是 LangChain 的官方 SDK 依赖——是「拿开源 SDK 的类型系统当底座，方言差异打补丁」。

**`ApiBackend` 三个变体，对照 Codex `WireApi` 的单变体**（`xai-grok-sampling-types/src/types.rs:1013-1021`）：

```rust
pub enum ApiBackend {
    #[default]
    ChatCompletions,   // /v1/chat/completions
    Responses,         // /v1/responses
    Messages,          // /v1/messages —— 原生 Anthropic 方言
}
```

三个细节都有信息量：**默认值是 ChatCompletions，但自家 grok-4.5 配的是 Responses**——默认值是给第三方端点留的，跟 Codex「删光 Chat Completions、留一个报错锚点逼你兼容我」正好相反；**Messages 变体是原生 Anthropic 兼容**（client.rs:4-8 明说 "Talks to three backend shapes"），兼容代价有专门方法处理（Messages 不支持 schema+tool 并存 → 降级走 StructuredOutput tool；要剥离 replayed reasoning，types.rs:1032-1042）；每 backend 一个独立的流 transform（`stream/mod.rs:1-9`）。本章第 5 节的谱系上，它插在 Pi（全抹平）和 Codex（全锁死）中间：抹平三种主流方言，不多不少。

**BYOK / 自托管是一等公民**，每模型可配：`base_url`（`shell/agent/config.rs:4131`）、`api_backend`、`auth_scheme`（Bearer / XApiKey 两种，`sampler/src/config.rs:20-24`）、`extra_headers`（types.rs:1057 原话 "for BYOK scenarios"）、`env_http_headers`（header 值从环境变量取，secret 不落盘）。模型目录本身可换源（`GROK_MODELS_BASE_URL`），解析优先级五级：CLI flag > ENV > config.toml > remote settings > 内嵌默认（`xai-grok-models/src/lib.rs:4-5`）。

**模型目录：运行时远端拉取 + 内嵌兜底只有 1 个模型**。`xai-grok-models` 整个 crate 只有 70 行——`default_models.json` 内嵌 grok-4.5（context_window 500k）一个条目，真实目录从 `{models_base_url}/models` 运行时拉。对照 Codex 的 bundled `models.json`（七模型七 prompt、编译期内建）：Grok 把模型元数据几乎全放服务端，客户端只留最小兜底。配套的 prompt 策略也一致地薄：**没有按模型分化的 prompt**，只有 `system_prompt_label` 换名字 + per-model `use_concise` 两档（详见第 03 章 Grok 节）——它没有 OpenAI「prompt 与模型协同训练」的包袱，也就不需要七份 prompt。

**重试与降级**（`sampler/src/retry.rs:8,51-62` 文档级注释）：最多 14 次重试（第 15 次 attempt 即 fatal），指数 + 平坦混合、全程 jitter，总预算约 5.5 分钟；429 单独降阈到 2 次；413/图片错误不计预算、剥图重试；服务端 `x-should-retry: false` 一票否决。两个独门设计：**首次重试用无连接池的 HTTP/1.1 fresh client**，逃逸中毒的 HTTP/2 连接池（`shared_http.rs:7-9` "first-retry HTTP/1.1 rebuild escape hatch"）；**doom loop 检测**——服务端下发信号，客户端可中途 abort 流，恢复预算耗尽后解除 abort 保证最后一次尝试完成（`doom_loop.rs:1-25`）。这是四个样本里唯一的「服务端参与的客户端止损」。而 LangChain 的看家能力——**模型间自动 fallback——没有**：sampler/retry 层查无此物（未确认更上层是否存在，倾向不存在）。

**镜像关系总结**：Codex 用类型系统筑护城河（单变体 + 报错锚点），Grok 用同一个 Rust 枚举开三扇门（含直接说竞品 Anthropic 的方言）。同为「模型厂商自家的 agent」，一个在锁定、一个在拉客——这不是技术分歧，是市场位置的直接投影：领先者筑墙，追赶者修桥。

**本节未确认**：fork 的 async-openai 与上游的具体 diff 未读；`/models` 端点返回的完整 schema 未见服务端契约；模型间 fallback 在 sampler 之上的会话层是否存在，未逐行排查（doom loop 与 model-switch watch 通道存在，但未见自动切换逻辑）。
